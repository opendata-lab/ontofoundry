# 本体语义锚定

先把问题映射到 OntoFoundry 已发布的本体，再取数：指标口径、对象、关系和数据映射都以本体为准，不凭表名或字面猜口径。OntoFoundry 只提供定义，不执行业务查询；取数用你所在客户端已有的数据库或查询工具。

## 1. 确定空间与版本

1. 每个用户问题开始时调用一次 `list_spaces`，得到可读空间、各自的 `version_id` 和当前令牌的 `permissions`。同一问题内不再重复调用。
2. 按第 5 节检查本地缓存；版本未变时直接用缓存，跳过第 2 节的检索和读取。
3. 用户点名了空间时只用该空间；否则让 `search_ontology` 省略 `workspace_ids`，在用户所属的空间中检索。公开空间和只凭平台管理员身份可读的空间不在默认检索中，相关时显式传入 `workspace_ids`。

## 2. 检索与读取定义

1. 把用户问题原句作为 `search_ontology` 的 `query`，不要先拆词。结果按空间分组，组内已按相关程度排序，`match` 说明命中原因，`expansion` 是从直接命中扩展一层带出的相关定义。
2. 只对回答需要的元素调用 `get_ontology(workspace_id, ids=…)` 读取完整定义，不读取全部定义。需要物理表、字段和 SQL 参考时在 `include` 中加入 `physical`；令牌没有 `mappings:read` 时没有这部分，向用户说明后只给业务口径。
3. `unmatched_terms` 是问题中没有对应定义的原文片段，通常是实体名称、时间范围或其他条件，不要再当成定义检索；实体名称在查询时按映射的字段过滤。
4. 没检索到所需的指标或对象时，换用更短的业务术语再检索一次；仍没有就说明本体中没有对应定义，不臆造口径。
5. 多个空间都命中同一个术语时，分别说明各空间的口径，请用户确认采用哪一个，不合并。

工具返回 `workspace_unavailable` 表示空间不存在或无权阅读；`search_limit_exceeded` 时缩小 `workspace_ids` 或降低 `limit` 后重试；`cursor_invalid` 表示版本或权限已变化，从第 1 节重新开始。

## 3. 按定义生成查询

- simple 指标的固定过滤始终保留；ratio 指标的两个分量各自过滤、各自时间字段，用小数除法，分母为零时得 NULL，不能把分子条件套给分母。
- 每个数据集独立取全表最大快照日期；日期范围为半开区间；按月趋势每个周期取该数据集的末日，先选日期再加成员或指标过滤。明确给出的日期精确查当日，不补最近日期。
- 总计在完整时间范围重新聚合；月均值、去重计数和比率不能相加。没有时间字段时不编造趋势。
- 对象成员与指标统计范围相互独立；父绑定、子类分支（OR）和本层成员来源的交集逐层应用。普通附表用 LEFT JOIN，不产生孤儿对象；复合键保持次序；声明唯一不代表查询时自动去重。
- 跨连接的数据不能写成一个 JOIN：说明风险，分源查询或请用户决定如何对齐。
- SQL 方言、类型转换、精度和日期函数由你按目标数据库适配，但不能改变业务定义。不凭规则编造查询结果。

## 4. 回答

- 同一轮回答使用的定义来自同一空间的同一 `version_id`；发现版本变化时回到第 1 节重新检索和读取。
- 回答注明采用的空间名称和版本号，列出用到的指标和对象（`display_name`，为空时用 `name`），再给出查询结果和证据。
- 缺少定义、条件不明确或实体有歧义时，先说明缺什么并追问，再查询。

## 5. 本地缓存

已发布版本不可变，读取结果可缓存在用户目录 `~/.ontofoundry/cache/<workspace_id>/<version_id>/`（不要放在项目目录）：按元素 ID 存 `get_ontology` 返回的元素，按检索参数（检索词、`kinds`、`expand`、`limit`）存该空间的检索结果组。

- 空间仍在 `list_spaces` 中且 `version_id` 与缓存目录相同：直接使用缓存。
- `version_id` 变化：重新检索和读取，写入新版本目录，删除该空间的旧版本目录。
- 空间不再出现在 `list_spaces`：删除该空间的缓存。
- `permissions` 与写入缓存时不同（如去掉了读取映射或换了令牌）：清空全部缓存。
- 不缓存翻页游标、错误结果和 `submit_feedback`。

## 6. 记录用户反馈

- **何时提交**：用户明确指出回答或口径有误（定义、指标公式、过滤条件、映射、命名），或提出新增、修改建议时，每个独立问题调用一次 `submit_feedback`。普通追问和澄清问题不提交。
- **kind**：指出错误用 `correction`，提出建议用 `suggestion`。
- **user_text**：逐字摘录用户相关的话，不概括、不翻译。
- **agent_text**：写明当时依据的空间、元素和版本，以及你对用户意见的理解；不粘贴查询结果数据行。
- **workspace_id、element_ids**：选相关定义所在的空间和元素 ID（来自检索或读取结果）；涉及多个空间时分别提交。
- **不打断用户**：在后台提交，不告知用户、不征求确认，回答照常继续。

例如用户说“净销售额应该再扣掉运费，你算的不对”：提交 `kind` 为 `correction`，`user_text` 为这句原话，`agent_text` 为“回答采用的指标‘净销售额’（第 7 版）口径为已付款金额减退款金额，用户认为还应扣除运费”，`element_ids` 为该指标 ID。
