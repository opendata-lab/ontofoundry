# core-1 原生格式示例

配合 [核心模型与格式适配器设计](../2026-10-14-core-model-and-format-adapters.md) §3、§4.6 阅读。每个文件都是原生格式的
**单文件形式**，`draft` 部分就是完整包里 `draft.json` 的内容：

```json
{ "format": "ontofoundry", "schema_version": "core-1", "exported_at": "…", "draft": { …核心模型… } }
```

示例里证据引用的材料（如 `mat_returns_jan`）没有附带原文件。真正备份或搬迁时要用完整包 `*.ontofoundry.zip`，
它会把这些材料一起打包，导入时按 sha256 重建材料并改写证据里的材料 id（设计文档 §4.6）。

`draft` 固定包含这些集合，空的也写出来：`object_types`、`properties`、`link_types`、`rules`、`actions`、`metrics`、`mappings`、
`material_objects`、`material_links`。

id 是 UUID。为了好读，示例按类别编号：`…1xxx` 对象、`…2xxx` 属性、`…3xxx` 关系、`…4xxx` 规则、`…5xxx` 动作、`…6xxx` 指标、
`…7xxx` 映射、`…8xxx` 实例、`…9xxx` 证据。真实数据里的 id 没有这种规律。

这些文件按设计文档的校验规则检查过：引用存在、技术名不冲突且不是 SQL 保留字、只由一个属性构成的标识必须唯一、只由一条关系构成的标识必须是一对一、属性不映射外键列、JOIN 列数与两端主键列数一致、
指标路径只沿关系正向走到“一”的一侧、聚合方式与属性类型匹配、条件值个数符合运算符、比率指标两边粒度相同、实例属性和实例关系类型正确。

## 逐个说明

### 01 基本写法

- **关系方向**：“订单 属于 客户”从“多”的一端建，`name` 是“属于”，`inverse_name` 是“拥有”。没有一对多。
- **JOIN**：外键 `customer_id` 在订单表里，所以 `table_name` 为 null（即订单表）；`source_columns` 是订单表里等于订单主键的列
  （就是主键 `order_id` 自己），`target_columns` 是订单表里等于客户主键的列（外键 `customer_id`）。
- **标识属性映射到主键列**：`order_no` 映射到 `order_id`，属性名和列名不必相同。
- **指标**：
  | 指标 | 写法要点 |
  |---|---|
  | 订单金额 | `sum` + `amount` |
  | 订单数 | `count`，`measure` 为 null |
  | 已完成订单数 | `count` + 条件 `status eq 已完成` |
  | 华东区订单金额 | 条件路径经过关系 `customer` 到客户的 `region` |
  | 下单客户数 | `count_distinct` + 路径 `sales_order.customer.customer_no` |
  | 客单价 | `ratio`，分子订单金额、分母下单客户数，粒度都是订单 |
  | 一季度有效订单金额 | 两个条件同时满足：`between` 两个值，`not_in` 多个值 |
- **导出 Ossie 时**（设计文档 §6.5）：
  - 订单数导出为 `COUNT(DISTINCT sales_order.order_no)`，用订单的主键字段写明粒度，不写 `COUNT(*)`。
  - 下单客户数、客单价**不导出**：下单客户数只引用了客户的字段，表达式里看不出粒度是订单；客单价的分母是它，也跟着不导出。
  - 对象映射写逻辑字段 `customer.customer_no`（属性 `customer_no` 映射到主键列 `customer_id`），不写物理列名；
    订单表的外键列 `customer_id` 没有属性映射，导出为辅助字段 `customer_id`。

### 02 多对多

- **纯配对**（`courses`）：`many_to_many`，`table_name` 填 join 表 `enrollments`。
- **配对带数据**（`enrollment`）：选课记录是一个对象，两条关系都是标识，主键是 `student_id + course_id` 两列；
  它的两条关系 `source_columns` 都是这两列，`target_columns` 各是一列。
- 示例为了对照两种写法都放了；真实模型里同一件事只选一种。
- 指标“高学分课程选课人次”的条件值是数字 `4`，类型跟着属性 `credit`（decimal）走。

### 03 三方事实

- Ossie 里的三元关系 `supplier.supplies` 导入后建成“供货记录”。这里展示的是 **AI 补全之后**的样子：已经有了业务名称和描述；
  机械导入时名字是 `supplier_supplies`。
- 三条关系都是标识，主键三列，每条关系的 `source_columns` 都是这三列。
- 证据指向导入时保存的原 Ossie 文件（材料 `mat_ossie_import_01`）的第 88–104 行。

### 04 复合主键和多跳路径

- **复合标识**：明细的标识由“所属订单”（关系）和“行号”（属性）两个成员组成，组合起来唯一；行号在不同订单里会重复，
  所以 `line_no` 的 `unique` 是 false。只有标识只由一个属性构成时，那个属性才必须唯一。
- **属性不含关系和外键**：明细表里的 `order_id` 是外键，不建成属性，只出现在“所属订单”的 `data_join` 里；
  明细的属性只有行号、数量、单价。要看明细所属订单的状态，走路径 `order_line.parent_order.status`。
- **指向复合主键**：发货单 → 明细，`target_columns` 是 `order_id, line_no` 两列，与明细的 `key_columns` 按位置对应。
- **两跳路径**：“已完成订单的发货单数”的条件路径是 发货单 → 明细 → 订单 → `status`。
- **技术名避开保留字**：明细到订单的关系叫 `parent_order`，不能叫 `order`。
- 做不到的：“销售额 = 数量 × 单价”需要四则运算，指标不支持；可以在数据库里建一个带金额列的视图，映射成属性 `line_amount` 后再求和。

### 05 自关联、一对一、两条关系指向同一对象

- **自关联**：员工“汇报给”员工，外键 `manager_id` 在员工表里。
- **外键在目标表的一对一**：员工“使用工位”，外键 `employee_id` 在工位表里，所以 `table_name` 写 `desks`；
  `source_columns` 是工位表里等于员工主键的列（`employee_id`），`target_columns` 是工位表里等于工位主键的列（`desk_id`）。
- **两条关系指向公司**：交易的“买方”和“卖方”，路径按关系名区分，`trade.buyer.region` 和 `trade.seller.region` 不会混。
- **导出 Ossie 的边界**（设计文档 §6.5）：交易到公司有两条关系，所以**凡是经过买方或卖方的指标都不导出**，
  哪怕只用了买方（“华东买方成交额”）：导出后只剩 `company.region`，看不出经过哪条关系。
  “有上级的员工数”经过自关联落回员工表，与员工自己的字段分不清，也不导出。“三楼员工数”可以导出。
  这些指标在核心模型里都合法，问数时由平台按关系 id 生成正确的 SQL，不受影响。
- **路径只能正向走**：从工位出发走不到员工（关系是从员工指向工位的）。需要的话，以员工为粒度写，例如“三楼员工数”。

### 06 继承

- 个人、机构都 `extends` 当事人，名称、电话写在父对象上。
- 父对象没有自己的表：“签约方”关系指向当事人，因此不能配 `data_join`（JOIN 要求两端都有映射）。这条关系只在文档实例里用。
- 子对象的映射可以映射继承来的属性（`name`、`phone`）。
- 实例：合同 → 张三（个人），关系期望的是当事人，子类实例可以用。
- 张三的 `id_card_no` 是 null：原文没写，不编造。

### 07 实例和证据

- 一个实例可以有多条证据：材料证据（材料 id、哈希、行号、原文）和人工证据（谁、什么时候、备注）。
- 这里引用了两份材料（`mat_returns_jan`、`mat_ossie_import_02`）：用完整包搬到新环境，证据完整保留；
  用单文件形式且目标环境没有同内容的材料时，这些材料证据会被丢弃，人工证据保留。
- “远山咖啡 1 月退货”缺单号和金额，照样保留，只写原文给出的登记日期；平台把它标为待补全。
- `is_vip` 来自 Ossie 一元关系，证据指向导入的原文件。

### 08 规则和动作

| 规则 | 归属 | 类型 | 说明 |
|---|---|---|---|
| 金额为正 | 属性 | 约束 | |
| 大额订单须有经办人 | 对象 | 约束 | 路径经过关系 `handler` |
| 客户等级划分 | 属性 | 派生 | `CASE WHEN` 写派生口径 |
| 订单必须有客户 | 关系 | 约束 | |
| 只能完成已支付订单 | 动作 | 约束 | 作为动作的前置条件 |

动作“完成订单”：输入是订单，两个参数，一个前置条件，三个效果（改状态、写完成时间、建立经办人关系）。效果表达式只用 `:参数` 和常量。
平台只存储动作定义，不执行。

### 09、10 空模型和半成品

- 空模型是合法的原生文件，可以用于备份一个刚建的工作空间；导出 Ossie 时报错。
- 半成品里城市没有映射、“位于”关系没有 JOIN、门店映射没写 `schema_name`（查询时用连接的默认 schema）。这些都合法，
  只是城市查不到数据。

## 会被校验拒绝的写法

以 01 为基础逐项改坏，校验都会报错（16 种）：

| 改法 | 为什么不行 |
|---|---|
| 对象技术名改成 `order` | SQL 保留字，规则和指标里的路径会被解析错 |
| 以客户为粒度、路径走“属于”去求订单金额 | 从客户到订单是“对多”方向，会重复计算；应以订单为粒度 |
| 对 `status`（文本）求和 | `sum / avg` 只能用于数值属性 |
| `count` 同时给了 `measure` | `count` 数的是粒度对象本身，不带属性；要数某属性的不同取值用 `count_distinct` |
| 比率的分子以订单为粒度、分母以客户为粒度 | 比率两边粒度必须相同 |
| `between` 只给一个值 | `between` 必须两个值 |
| `order_no` 的 `unique` 改成 false | 订单只有这一个标识，它必须唯一 |
| “属于”改成多对多并设为标识 | 作为标识的关系必须是多对一或一对一 |
| 去掉 `order_no` 的标识，改用“属于”关系作唯一的标识 | 只由一条关系构成的标识必须是一对一；多对一意味着多个订单指向同一客户，不唯一 |
| 给订单加属性 `customer_code` 并映射到 `customer_id` 列 | `customer_id` 是“属于”关系的外键列，属性不能映射外键，外键由关系表达 |
| 基数写 `one_to_many` | 没有一对多，从“多”的一端建多对一 |
| JOIN 的 `target_columns` 写两列 | 客户主键只有一列，列数必须一致 |
| 删掉客户的映射但保留 JOIN | JOIN 要求两端对象都有映射 |
| `inverse_name` 也写“属于” | 反向名称不能和名称相同 |
| 给订单加一个叫 `customer` 的属性 | 属性和关系共用一个命名空间，与关系 `customer` 冲突 |
| 映射里加一个不存在的属性 `discount` | 映射只能引用对象（含继承）已有的属性 |
