# 表结构证据与结构化本体发现（P0）

日期：2026-10-21。状态：已确认，待实施（路线图步骤 2，用户授权按计划推进）。来源：Codex 核心竞争力方案“结构化来源收据”、语义锚定路线图 P0。

## 1. 问题

建模运行中，已关联表的结构作为临时文件上传给 DataAgent（`api/agent_conversation.py` 中的 `ontofoundry-tables-<run>.json`），平台不留存。由表结构得出的实体、属性、关系没有可校验的证据：审阅人看不到“这个属性来自哪张表的哪一列”，事后也无法回放当时的表结构。

## 2. 决定

| 编号 | 决定 | 状态 |
|---|---|---|
| TE-01 | 不新增证据类型。建模运行把本轮实际使用的表结构 JSON 存为平台材料（“表结构收据”），与文档材料一样按内容哈希去重；表来源的元素引用它的行号作为材料证据，校验规则沿用现有（材料属于空间、哈希一致、行号在范围内、引用原文出现在对应行）。 | 已确认 |
| TE-02 | 收据内容即现有的 `tables_file` 结构（连接名、库、表、类型、注释、主键、外键、列名、物理类型、可空、列注释），用固定格式（`indent=2`，键按固定顺序）序列化，保证同样的结构得到同样的内容和行号。不含连接凭据和业务数据行。 | 已确认 |
| TE-03 | 材料记录新增 `origin`（`upload`／`table_receipt`），区分用户上传的文档与平台生成的收据；“文档”Tab 默认只列上传文档，收据在证据中可查看。新增 Alembic 迁移，已有材料取 `upload`。 | 已确认 |
| TE-04 | 收据随运行写入 manifest 的材料清单，`material_lookup` 与证据校验按普通材料处理；同一工作包内的结构不因后台同步而变化。 | 已确认 |
| TE-05 | 外键、同名字段只作为关系候选的证据；没有业务依据（材料说明或明确的外键约束）时只在交付说明中列出，不直接提出关系提案。 | 已确认 |
| TE-06 | 表分类由 Agent 在方法中判断，不进入核心模型：先判断一行代表什么（实体、事件、明细、某时点状态、汇总），再决定建成实体、属性、关系、指标来源还是只作数据集；表名前缀（如 `dim_`、`dwd_`、`dws_`）、字段名相似只作线索。 | 已确认 |

## 3. 实现要点

- 后端：建模运行组装工作包时，用 `store_text_material` 保存收据（名称如“表结构收据 · <连接名> · <YYYY-MM-DD>”），`origin = table_receipt`，把它加入 manifest 的 `materials`（带行号文件路径），上传给 DataAgent 的仍是同一份内容。
- 材料列表、材料用量和删除规则：收据被证据引用时与文档同样受保护；“文档”Tab 增加来源筛选，默认“上传的文档”。
- Skill（ontology-discovery，拆分前在 ontofoundry-modeling）：方法中补充表分类判断（TE-06）、外键与同名字段的用法（TE-05），以及“表来源元素引用收据行号作为证据”的写法与示例（示例用虚构领域）。
- 证据弹窗：收据证据显示为“表结构收据 · 表名 · 列名”，引用原文为对应 JSON 行。

## 4. 验收

- 同一组表两次运行得到同一份材料（哈希一致），结构变化后得到新材料，旧提案证据仍可校验。
- 表来源属性的证据通过本地检查与平台校验；引用了收据外行号或错误原文时被拒。
- “文档”Tab 默认不显示收据；被引用的收据不能删除。
- Skill 离线检查通过；真实建模验收待用户安排（DeepSeek）。

## 5. 不做

- 不新增核心证据类型或“表角色”字段。
- 不保存业务数据行，不接入外部血缘。

## 6. 实施结果

- 范围：实施 TE-01 至 TE-04 的后端。表结构收据使用普通材料的存储、分块、哈希去重、材料查找、证据行号校验、用量统计、归档和删除保护；不增加核心证据类型。收据随运行占用声明一并写入 manifest，工作包材料索引和 `tables_file` 指向同一份上传内容，后台同步不会改变本轮内容。
- 来源字段：`origin` 是本平台自创的材料管理元数据，不是核心业务语义，也不是查询执行优化。删除它将无法可靠区分上传文档与平台生成收据；材料名称和 JSON 内容均不能可靠替代。材料列表、概览、上传、归档和恢复响应返回 `upload` 或 `table_receipt`；迁移为已有记录填入 `upload`，并保留数据库默认值。前端已有兼容的可选类型，无需修改。
- 固定格式：沿用现有 `tables_file` 字段，显式按固定顺序生成各层对象，`indent=2`、`ensure_ascii=False`、UTF-8、无额外末尾换行。表按连接 ID、库名、表名排序后编号；外键按约束列和引用目标的固定内容排序，保留物理列、主键列和外键内部列的顺序。连接配置、凭据、同步时间和业务数据不写入收据。
- 命名规则：单连接为“表结构收据 · <连接名> · <YYYY-MM-DD>”；多连接将本轮全部表存为一份材料，名称为“表结构收据 · 多连接（N） · <YYYY-MM-DD>”，N 按连接 ID 去重计数。日期取首次创建时的 UTC 日期，单连接名称中的路径分隔符替换为全角字符，连接名最多保留 200 字符。名称和日期不参与内容哈希，相同内容沿用首份记录的名称及来源；跨来源同内容也不重复建记录。
- 偏离设计之处：无语义或契约层面的偏离。补充了表排序、外键排序、多连接命名、UTC 日期和跨来源去重规则；证据校验同时显式拒绝小于 1 或倒序的行号。TE-05、TE-06、DataAgent 技能与提示词、前端筛选和证据弹窗均不在本次后端范围。
- 测试结果：全部编辑完成后，在 `apps/api` 执行 `.venv/bin/python -m pytest -q`，最终 **1112 通过、17 跳过、0 失败、0 错误**，耗时 104.65 秒，另有 3 条现有依赖或模型警告；`.venv/bin/ruff check src tests evals` 全部通过。新增 12 个用例覆盖重复组装、勾选顺序和日期变化、结构变更后的历史证据、多连接命名、JSON 键和外键排序、manifest 与上传字节一致、后台同步隔离、非法行号/引文/哈希/空间、来源读接口、证据用量与删除保护、归档后源文件恢复和 Alembic 升降级。
- 回归修复：首轮全量测试发现已有后端测试仍引用 DataAgent 拆分前的资源路径；仅修改 4 个后端测试文件的只读资源路径，并调整增量场景的材料清单断言，未修改 `integrations/dataagent`。第二轮全量测试通过。
