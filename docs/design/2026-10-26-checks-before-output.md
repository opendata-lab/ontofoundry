# 检查串在产出之前，去掉修复任务和平台消息

日期：2026-10-26。状态：用户已确认方向（内网验证反馈），实施中。替代 `2026-10-23-proposal-checks-in-conversation.md` 的 CK-01 中“平台不可达时说明未做检查”和 CK-03 全部内容。

## 1. 背景

内网验证时有两个问题：

1. **产出提案后又冒出一轮修复。** 页面先报“事件流意外结束”，接着出现新一轮“深度思考”，开始“建模修复”。原因有两层：
   - 运行内的合并脚本连不上平台检查接口时，只输出“提示 [PLATFORM_CHECK_SKIPPED]”，照样写出最终结果；
   - 平台入库时再按同一套规则检查，不通过就自动发起“建模修复”任务。新任务接管会话后，旧任务的事件流断开，所以界面先报错，再开始新一轮。
   - 用户看来，检查是在产出之后补的，修复是另起的一条旁路。
2. **增量建模时英文标识重复。** 例如本体已有 29 个定义，再提一个增量需求，新提案里会把已有概念重建一遍，与草稿中的定义重名，被判为不可接受。原因是计划步骤把已有概念也列进清单（标“已有”），抽取步骤却没有说明已有概念不要重建。

另外，对话里的“平台消息”（失败原因加“重试”按钮）和对话内容分开显示，像一条旁路，用户不想要。

## 3. 改动

- 技能：
  - `prepare_result.py`：平台检查连不上或结果无效时，返回错误 `PLATFORM_CHECK_UNAVAILABLE`，不写最终结果；
  - `finish.md`：两轮修正后的处理（CO-02）；
  - `extract.md`：已有概念不重建（CO-05）。
- 平台：
  - 删除 `_request_repair`、`build_proposal_repair_request` 和“模式：建模修复”提示；
  - 入库拒收时，运行以 `failed_permanent` 结束，失败原因写入运行状态说明；
  - 删除 `proposal_notice` 字段、`run_notice` 和 `ontofoundry.proposal-run-notice.v1` 契约。
- 构建页：删除平台消息和“重试”按钮；UI 视觉文档中“建模平台消息（2026-10-23）”一节改为指向本设计。
- 不变：
  - 运行内修正计数（工作包的 `execution`）；
  - 入库时逐组判定可接受与否；
  - 提案面板的“不可接受”页签。

## 4. 入库还会失败的情况

对话中的合并脚本已经用平台同一套规则检查过结果，入库不会再因为内容被拒。剩下的失败只有以下几类，都在提案面板显示“本轮没有产出提案”和原因：

- 运行没有产出结果文件：Agent 中途放弃、轮数用完、模型报错或超时、用户停止，或者平台检查不可达。对话里通常已有 DataAgent 的错误提示，或 Agent 的说明。
- 结果文件下载失败：DataAgent 文件服务长时间不可用，三次重试后仍失败。
- 检查后结果文件被改写：模型绕过合并脚本直接写文件，极少见。
- 运行期间会话被放弃，固定上下文失效。
