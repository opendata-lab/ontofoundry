# 接受时补全：缺值、绑定与数字类型

日期：2026-11-15。状态：AC-03 已实施（数字类型），其余待实施。来源：用户 2026-11-15 决定（“提案可以不完整，接受时必须修好”）；Codex 校验阶段审查（`~/.agents/handoffs/2026-11-15-codex-validation-review/`）列出的缺口 1。

## 1. 问题

智能体提交的提案可以不完整，但目前接受时也不检查，缺口直接进入模型：

| 情形 | 现在 | 后果 |
|---|---|---|
| 发货单 `{数量: null}`，数量为必填 | 接受，读取时提示“待补全” | 模型里留下缺值实例 |
| 订单已绑定 `orders`，新属性 折扣 没有对应列 | 接受 | 订单之后显示“属性绑定待补全”，不能查询 |
| 订单已绑定 `orders`，没有来源逻辑键 | 接受 | 订单状态为 `missing_key`，不能查询 |
| 会员 `{会员号: "42"}`，会员号为整数 | 接受，按文本原样保存 | 与已有的 `42` 比较不相等，重复候选找不到 |

## 2. 决定

| 编号 | 决定 | 来源 |
|---|---|---|
| AC-01 | **提案可以不完整，接受时必须完整。** 提交与修订批次照旧放行；接受前逐项检查，有问题就拒绝，并列出元素和属性。沿用已有先例：未绑定连接的数据集可以出现在提案里，接受时必须绑定（`services/proposal_apply.py` 的 `accepting`）。 | 用户 2026-11-15 |
| AC-02 | **文档实例缺必填或标识属性，接受时拒绝。** 取代主设计 §3.9“文档事实缺标识仍保存并提示补全，不因 required/identifier 自动拒绝”。原文确实没有的值，由审阅者在会话里请智能体补、手工修改提案，或拒绝提案，或把属性改为非必填。 | 用户 2026-11-15 |
| AC-03 | **接受的文档实例中，整数、小数、浮点属性必须是数字**，`"42"` 拒绝，报“到店次数（visits）必须是整数，不能写成文本 '42'”。只查本次接受的实例；提案与读取不变，已存实例不被过滤，不做数据迁移。数据库实例不受影响（小数以文本传出以保留精度）。 | 用户 2026-11-15 |
| AC-04 | **已绑定表的对象，接受后必须完整：** 有来源逻辑键，每个有效属性都绑定到列。没有表的对象（只有文档实例的对象、虚拟父对象）不检查。“来源列元数据待补全”（通常是连接离线或未同步）只提示，不阻止。按接受后的结果判断：同一次接受里补上映射即可通过。 | 用户 2026-11-15 |
| AC-05 | **审阅界面标出不能直接接受的提案：** 卡片上显示警示图标，悬停列出问题；状态标签旁增加“待补全 N”筛选。问题在批次读取时推导，不存储（同 `source_diagnostics`）。 | 用户 2026-11-15 |
| AC-06 | **补全方式就是会话。** 审阅者在建模会话里说明问题，智能体修订批次，直到提案可以接受。不新增按钮，不改技能。 | 用户 2026-11-15 |

## 3. 消息

每条问题说明元素和属性，审阅者可以直接复制到会话里：

- `发货单 #3：数量（quantity）待补全`
- `订单：属性 折扣（discount）未绑定列`
- `订单：来源逻辑键待补全`
- `到店次数（visits）必须是整数，不能写成文本 '42'`

## 4. 与现有文档的关系

- 主设计 `2026-10-14-core-model-and-format-adapters.md` 第 498 行“不因 required/identifier 自动拒绝”改为“接受时拒绝”（AC-02）。
- 多元关系的角色编号属性（`docs/concepts/identifiers.md`、`link-types.md`）在外键指向物理键时“编号绑定待补全”，与 AC-04 冲突。用户决定（2026-11-15）：多元关系不再生成角色编号属性，直接用参与对象表上的多个键列关联。这是导入方式的变化，单独实施，记录在 `docs/TODO.md`；在它完成前，这类属性按 AC-04 不能接受。

## 5. 不在本次范围

Codex 审查的其他缺口记录在 `docs/TODO.md`“建模质量”，各自另议：值类型约束不作用于实例值（文档互相矛盾）、表达式不检查布尔结果、相同业务标识的实例只提示、关系实例不检查声明基数、列元数据缺失时未知列无提示、校验报告未检查实例却显示通过。
