# 接受时检查：定义与实例

日期：2026-11-15。状态：AC-03（PR #75）、AC-12（PR #76）已实施；AC-01、02、04、05、08、09、10、11 见[实施计划](../plans/2026-11-15-accept-completeness-plan.md)；AC-07 已实施（`domain/rule_evaluation.py`）；验证待实施。来源：用户 2026-11-15 决定（“提案可以不完整，接受时必须修好”）；Codex 校验阶段审查（`~/.agents/handoffs/2026-11-15-codex-validation-review/`）；Codex 对本设计的审查（`~/.agents/handoffs/2026-11-15-codex-accept-checks-review/`），其中的实现约束已并入 AC-04、AC-07。

## 1. 问题

智能体提交的提案可以不完整，但目前接受时也不检查，缺口直接进入模型：

| 情形 | 现在 | 后果 |
|---|---|---|
| 发货单 `{数量: null}`，数量为必填 | 接受，读取时提示“待补全” | 模型里留下缺值实例 |
| 订单已绑定 `orders`，新属性 折扣 没有对应列 | 接受 | 订单之后显示“属性绑定待补全”，不能查询 |
| 会员 `{会员号: "42"}`，会员号为整数 | 接受，按文本原样保存 | 与已有的 `42` 不相等，重复候选找不到 |
| 会员等级只允许 普通／金卡，实例填“钻石” | 接受，规则不执行 | 违反约束的值进入模型 |

## 2. 原则

| 编号 | 决定 | 来源 |
|---|---|---|
| AC-01 | **提案可以不完整，接受时必须完整。** 提交与修订批次照旧放行；接受前检查，有问题就拒绝，并列出元素和属性。沿用已有先例：未绑定连接的数据集可以出现在提案里，接受时必须绑定（`services/proposal_apply.py` 的 `accepting`）。 | 用户 2026-11-15 |
| AC-05 | **审阅界面标出不能直接接受的提案：** 卡片上显示警示图标，悬停列出问题；状态标签旁增加“待补全 N”筛选。问题在批次读取时推导，不存储（同 `source_diagnostics`）。 | 用户 2026-11-15 |
| AC-06 | **补全方式就是会话。** 审阅者在建模会话里说明问题，智能体修订批次，直到提案可以接受。不新增按钮，不改技能。 | 用户 2026-11-15 |
| AC-08 | **定义检查与实例检查分开。** 批次里有定义才做定义检查；有文档实例才做实例检查，且只查本次接受的实例。只接受定义时不回查已存实例：新增规则 `金额 >= 0` 不回查已有 500 条订单，只约束此后接受的实例。 | 用户 2026-11-15 |

## 3. 定义检查

批次含对象、属性、关系、映射或规则时，接受前检查：

| 编号 | 决定 | 来源 |
|---|---|---|
| — | 现有的结构、引用、命名、继承、表达式检查不变。 | 已有 |
| AC-04 | **已绑定表的对象，接受后必须完整：** 有来源逻辑键，每个有效属性都有绑定（列或计算表达式均可）。没有表的对象（只有文档实例的对象、虚拟父对象）不检查。“来源列元数据待补全”（通常是连接离线或未同步）同样阻止，提示先同步表结构（同 AC-10，用户 2026-11-15 决定）。按接受后的结果判断：同一次接受里补上映射即可通过；为此，属性提案与同批中为它补绑定的映射更新互相依赖，接受任一项会一并接受另一项。比率指标按其分子分母指标所用的数据集检查；关系映射表所用的数据集同样须已同步；所用列的物理类型未知也算未同步。只查本次接受影响的对象（被改动的对象及共享其绑定的子对象），草稿里其他对象已有的缺口不连带阻止。实现从 `resolve_binding` 的来源与字段推导，不直接用 `binding_readiness` 的状态：后者在只缺列元数据时也返回 `unbound`，且共享父表的分支会提前返回、掩盖缺字段。 | 用户 2026-11-15 |
| AC-09 | **约束规则和成员条件必须是条件**（结果为真或假），否则拒绝：`规则「c1」必须是条件（结果为真或假）：sales_order.amount + 1`。现在 `amount + 1` 与 `amount > 100` 一样通过校验。 | 用户 2026-11-15 |
| AC-10 | **列信息未知时不能接受：** 数据集尚未同步列时，指标、映射、规则引用的列无法核对，现在静默通过。改为拒绝：`指标 total：列 ammount 无法验证，请先同步数据集 order_summary 的表结构`。同步后再接受，拼错的列随即被现有检查发现。代价是数据源离线时，用到它的提案暂时不能接受；那时这些列本来也无法核对。AC-04 的列元数据缺失按同一规则阻止。 | 用户 2026-11-15（起初定为提示，随后改为阻止） |

## 4. 实例检查

批次含文档实例时，对本次接受的实例检查：

| 编号 | 决定 | 来源 |
|---|---|---|
| AC-02 | **缺必填或标识属性，拒绝。** 空白文本视同缺值，不算类型错误；可选属性的空白值不报错。 取代主设计 §3.9“文档事实缺标识仍保存并提示补全，不因 required/identifier 自动拒绝”。原文确实没有的值，由审阅者在会话里请智能体补、手工修改提案、拒绝提案，或把属性改为非必填。 | 用户 2026-11-15 |
| AC-03 | **值必须符合属性类型**（见下表）。只查本次接受的实例；提案与读取照旧宽松，已存实例不被过滤，不做数据迁移。数据库实例不受影响（小数以文本传出以保留精度）。 | 用户 2026-11-15 |
| AC-07 | **执行约束规则：** 值类型约束和只引用本对象属性的对象／属性约束，接受时求值，不满足则拒绝，报属性、规则名和值。规则涉及其他对象（如 `sales_order.handler.employee_no IS NOT NULL`，自关联也算）或用到允许清单以外的写法时，提示“规则未检查”，不阻止。派生规则（derivation）不检查。空值不求值，由 AC-02 处理。实现：只对允许清单内的语法求值——比较、`IN`、`BETWEEN`、`AND/OR/NOT`、四则运算（用 `Decimal`，精确）、`LIKE`、`REGEXP_LIKE`（Python `re`，已在定义校验时限制写法）以及少量文本函数；清单外一律“未检查”。不采用“转成 SQLite 执行”：Codex 审查实测 `TRY_CAST('abc' AS INT) IS NOT NULL` 在 SQLite 中为真、`DECIMAL` 被转成浮点而丢失精度、`REGEXP` 与 `LEFT` 在 SQLite 中不存在，会静默得出错误结果。单对象判断复用 `resolve_rule_expression` 的解析结果：所有引用都不经关系跳转。取代值类型设计 §4.4“不为文档事实新建规则执行器”和 `docs/concepts/rules.md`“平台不执行规则”。 | 用户 2026-11-15 |
| AC-11 | **关系实例遵守声明基数：** 接受后，多对一关系的同一源实例只能连到一个目标，一对一两端都唯一。例：订单 O-028 已连客户 C-018，再接受连向 C-019 的关系，拒绝：`订单「O-028」：关系 所属客户 只能连一个，已连「C-018」`。只查本次接受的关系所涉及的源与目标。 | 用户 2026-11-15 |

AC-03 的类型规则：

| 类型 | 接受 | 拒绝 |
|---|---|---|
| 文本 | `"abc"` | `42`、`true` |
| 布尔 | `true` | `"true"`、`"是"`、`1` |
| 整数 | `42` | `"42"`、`42.0`、`true` |
| 小数、浮点 | `12.5`、`7` | `"12.5"`、`true` |
| 日期 | `"2026-01-20"` | `"2026/01/20"`、`"2026-02-30"`、`20260120` |
| 日期时间 | `"2026-01-20 10:12"`、`"2026-01-20T10:12:00+08:00"` | `"2026-01-20"`（缺少时间）、`"2026/01/20 10:12"` |

日期时间不要求时区：文档很少写时区，要求它只会让智能体编造。

**发布时的实例检查保留：** 发布时仍按新定义回查已存实例（`services/instance_store.py` 的 `publish_impact`），拦截两类：值与新类型不再相容（例：到店次数从整数改成文本，而已有实例存的是 3），以及实例所依赖的解释定义改变（属性类型、值类型、关系定义；例：整数改小数时，值 3 仍相容，但解释改变，同样阻止）。不套用本节更严格的规则。

## 5. 校验报告

| 编号 | 决定 | 来源 |
|---|---|---|
| AC-12 | **校验报告不再对未检查的实例显示“通过”。** 会话的校验报告只检查定义（AC-08），`instance_status` 为 `not_checked`；实例在接受和发布时检查。原先恒为 `passed`（`_instance_findings` 恒返回空列表，已删除）。 | 用户 2026-11-15 |
| AC-13 | **“必填”只写在属性上。** 只说某个本对象属性不为空的约束规则（`x IS NOT NULL`，可用 AND 连接多个）在提案和保存时退回：“是否必填在属性上设置，不写成规则”。来源：2026-11-17 验收中智能体把发货数量的必填改成这种规则，因空值不求值而绕过 AC-02。涉及其他对象或带其他条件的规则不受影响；已保存的规则不因此失效。 | 用户 2026-11-17 |
| AC-14 | **“全部接受”接受能通过的，列出没通过的。** 请求带 `partial` 时，接受检查把每个问题归到对应提案，这些提案及依赖它们的提案留在待审并附原因，其余照常接受；逐条接受或不带 `partial` 时仍整批成败。来源：2026-11-17 青禾 433 条中 6 条被拒，整批失败后逐条接受用了 46 分钟。 | 用户 2026-11-17 |

## 6. 消息

每条问题说明元素和属性；实例问题以“类型「实例标题或标识」”开头，同一批里多个实例的问题分别列出。审阅者可以直接复制到会话里：

- `发货单 #3：数量（quantity）待补全`
- `订单：属性 折扣（discount）未绑定列`
- `会员「C-018」：到店次数（visits）必须是整数，不能写成文本 '42'`
- `会员「C-018」：入会时间（joined_at）必须是日期时间，缺少时间：'2026-01-20'`
- `会员「C-018」：会员等级（member_level）不满足约束「会员等级取值」：'钻石'`
