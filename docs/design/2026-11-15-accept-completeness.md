# 接受时检查：定义与实例

日期：2026-11-15。状态：AC-03 已实施（值类型匹配），其余待实施。来源：用户 2026-11-15 决定（“提案可以不完整，接受时必须修好”）；Codex 校验阶段审查（`~/.agents/handoffs/2026-11-15-codex-validation-review/`）的缺口 1、2。

## 1. 问题

智能体提交的提案可以不完整，但目前接受时也不检查，缺口直接进入模型：

| 情形 | 现在 | 后果 |
|---|---|---|
| 发货单 `{数量: null}`，数量为必填 | 接受，读取时提示“待补全” | 模型里留下缺值实例 |
| 订单已绑定 `orders`，新属性 折扣 没有对应列 | 接受 | 订单之后显示“属性绑定待补全”，不能查询 |
| 会员 `{会员号: "42"}`，会员号为整数 | 接受，按文本原样保存 | 与已有的 `42` 不相等，重复候选找不到 |
| 会员等级只允许 普通／金卡，实例填“钻石” | 接受，规则不执行 | 违反约束的值进入模型 |

## 2. 原则

| 编号 | 决定 | 来源 |
|---|---|---|
| AC-01 | **提案可以不完整，接受时必须完整。** 提交与修订批次照旧放行；接受前检查，有问题就拒绝，并列出元素和属性。沿用已有先例：未绑定连接的数据集可以出现在提案里，接受时必须绑定（`services/proposal_apply.py` 的 `accepting`）。 | 用户 2026-11-15 |
| AC-05 | **审阅界面标出不能直接接受的提案：** 卡片上显示警示图标，悬停列出问题；状态标签旁增加“待补全 N”筛选。问题在批次读取时推导，不存储（同 `source_diagnostics`）。 | 用户 2026-11-15 |
| AC-06 | **补全方式就是会话。** 审阅者在建模会话里说明问题，智能体修订批次，直到提案可以接受。不新增按钮，不改技能。 | 用户 2026-11-15 |
| AC-08 | **定义检查与实例检查分开。** 批次里有定义才做定义检查；有文档实例才做实例检查，且只查本次接受的实例。只接受定义时不回查已存实例：新增规则 `金额 >= 0` 不回查已有 500 条订单，只约束此后接受的实例。 | 用户 2026-11-15 |

## 3. 定义检查

批次含对象、属性、关系、映射或规则时，接受前检查：

| 编号 | 决定 | 来源 |
|---|---|---|
| — | 现有的结构、引用、命名、继承、表达式检查不变。 | 已有 |
| AC-04 | **已绑定表的对象，接受后必须完整：** 有来源逻辑键，每个有效属性都绑定到列。没有表的对象（只有文档实例的对象、虚拟父对象）不检查。“来源列元数据待补全”（通常是连接离线或未同步）只提示，不阻止。按接受后的结果判断：同一次接受里补上映射即可通过。 | 用户 2026-11-15 |

## 4. 实例检查

批次含文档实例时，对本次接受的实例检查：

| 编号 | 决定 | 来源 |
|---|---|---|
| AC-02 | **缺必填或标识属性，拒绝。** 取代主设计 §3.9“文档事实缺标识仍保存并提示补全，不因 required/identifier 自动拒绝”。原文确实没有的值，由审阅者在会话里请智能体补、手工修改提案、拒绝提案，或把属性改为非必填。 | 用户 2026-11-15 |
| AC-03 | **值必须符合属性类型**（见下表）。只查本次接受的实例；提案与读取照旧宽松，已存实例不被过滤，不做数据迁移。数据库实例不受影响（小数以文本传出以保留精度）。 | 用户 2026-11-15 |
| AC-07 | **执行约束规则：** 值类型约束和只引用本对象属性的对象／属性约束，接受时求值，不满足则拒绝，报属性、规则名和值。规则涉及其他对象（如 `sales_order.handler.employee_no IS NOT NULL`）或使用 SQLite 无法执行的函数时，提示“规则未检查”，不阻止。派生规则（derivation）不检查。空值不求值，由 AC-02 处理。实现：sqlglot 把规则转成 SQLite 方言，在内存 SQLite 中对一行实例值求值，沿用规则的 SQL 语义，不另写解释器。取代值类型设计 §4.4“不为文档事实新建规则执行器”和 `docs/concepts/rules.md`“平台不执行规则”。 | 用户 2026-11-15 |

AC-03 的类型规则：

| 类型 | 接受 | 拒绝 |
|---|---|---|
| 文本 | `"abc"` | `42`、`true` |
| 布尔 | `true` | `"true"`、`"是"`、`1` |
| 整数 | `42` | `"42"`、`42.0`、`true` |
| 小数、浮点 | `12.5`、`7` | `"12.5"`、`true` |
| 日期 | `"2026-01-20"` | `"2026/01/20"`、`"2026-02-30"`、`20260120` |
| 日期时间 | `"2026-01-20 10:12"`、`"2026-01-20T10:12:00+08:00"` | `"2026-01-20"`（缺少时间）、`"2026/01/20 10:12"` |

日期时间不要求时区：文档很少写时区，要求它只会让智能体编造。

**发布时的实例检查保留：** 发布时仍按新定义回查已存实例（`services/instance_store.py` 的 `publish_impact`），只拦截因定义变化而无法解释或类型不再相容的实例（例：到店次数从整数改成文本，而已有实例存的是 3），不套用本节更严格的规则。

## 5. 消息

每条问题说明元素和属性，审阅者可以直接复制到会话里：

- `发货单 #3：数量（quantity）待补全`
- `订单：属性 折扣（discount）未绑定列`
- `到店次数（visits）必须是整数，不能写成文本 '42'`
- `入会时间（joined_at）必须是日期时间，缺少时间：'2026-01-20'`
- `会员等级（member_level）不满足约束「会员等级取值」：'钻石'`
