# Entity Resolver：实例链接与消歧

日期：2026-10-21。状态：已实施（2026-10-22）。来源：用户 2026-10-21 与 ChatGPT 讨论中的“Entity Resolver：统一实体链接与消歧”及当日决定。

## 1. 目标

问题或材料中的实体提及（如“星河电子”）在给定实体类型下找到对应实例，并明确告诉调用方是唯一命中、有歧义还是没找到。Agent 不得按名称取第一个结果。

现状：`search_objects` 只搜文档实例；数据库实例搜索（REST）对主键和各字段做“包含”匹配，按主键排序，不返回匹配状态。

## 2. 决定

| 编号 | 决定 | 状态 |
|---|---|---|
| ER-01 | 新增 MCP 工具 `resolve_entity`，输入 `mention`、`object_type_id`（UUID，不接受英文标识或名称），可选 `limit`（默认 10，上限 50）。空间与版本由令牌绑定。 | 已确认 |
| ER-08 | 同一解析服务提供两个入口：MCP 工具 `resolve_entity` 与 REST `POST /api/v1/ontology/workspaces/{workspace_id}/entities/resolve`。候选检索、判级、定状态全部在 Python 服务中确定性完成；Skill 只负责何时调用、`AMBIGUOUS` 时如何追问，不在提示词里做匹配。 | 已确认（2026-10-21） |
| ER-02 | 匹配级别：① 业务标识属性精确命中；② 标题属性精确命中；③ 标题属性包含命中。语义（向量）召回与上下文消歧本期不做。 | 已确认 |
| ER-03 | 状态：`MATCHED`（① 或 ② 唯一命中；或仅有一条 ③ 包含命中）、`AMBIGUOUS`（同一最高级别多条命中）、`NOT_FOUND`。仅一条包含命中时视为 `MATCHED`，调用方在回答中写明按哪个实例理解。 | 已确认 |
| ER-04 | 不输出数值分数；每个候选返回命中级别与命中的属性和值。分数待有标注样本校准后再考虑。 | 已确认 |
| ER-05 | 名称规范化：只做去首尾空白、Unicode NFKC、英文小写三步，用于判定精确／包含；不做去“有限公司”、简称、曾用名、拼音。 | 已确认（2026-10-21） |
| ER-06 | 数据来源：实体类型有数据库映射时查业务库（只读，经现有实例查询计划与权限）；同时查已接受的文档实例。两处结果分别标注来源，不合并、不推断同一实体。 | 已确认（2026-10-21） |
| ER-07 | 不在平台建实体索引，每次解析直接只读查询源系统（见实例库设计 IS-03）。 | 已确认（2026-10-21） |
| ER-09 | 复合业务标识（如订单号 + 行号）只有给出完整元组才进入 ① 级；只给部分成员时不按标识命中，退回名称匹配并在结果中说明。不把成员拼接为新的身份。 | 已确认（2026-10-21，Codex 评审） |
| ER-10 | 唯一性针对完整授权范围判定：按级别从高到低分别计数，最高非空级别恰好一条才为 `MATCHED`；候选截断只影响展示，不影响状态。 | 已确认（2026-10-21，Codex 评审） |
| ER-11 | 结果按来源分流：业务库命中只用于查询、解释和审阅参考，不能作为实例更新目标；文档实例命中可作为“更新已有实例”的候选，仍需人工在审阅中确认，`MATCHED` 不自动升级为合并决定（与现行实例重复审阅规则一致）。 | 已确认（2026-10-21，Codex 评审） |
| ER-12 | 粗筛不能保证覆盖规范化写法（如源值为全角、输入为半角）时，无候选返回 `NOT_FOUND` 并附 `coverage: "partial"` 与原因，调用方不得据此断言实体不存在。 | 已确认（2026-10-21，Codex 评审） |
| ER-13 | 运行凭据固定为 `ontology:read`、`instances:read`、`mappings:read`，所有建模运行相同，不按运行类型区分（内网使用，简单优先）；只读，绑定发起人（不超过其本人权限）、空间、运行和固定版本，运行结束失效。业务库候选（名称、编码等）会进入 Agent 上下文并发送给所用模型，用户已知悉并同意。 | 已确认（2026-10-21） |

## 3. 匹配过程

1. **分级查询**：按 ① ② ③ 顺序分别查询，每级先取 `count`（上限 `limit + 1` 即可判定是否多于一条），找到最高的非空级别后停止（ER-10）。业务库按映射生成只读查询；文档实例按同样属性在实例值上匹配。粗筛对业务标识和标题列做不区分大小写的匹配，并同时尝试输入的半角与全角写法以减少漏召（ER-12）。
2. **判级**：对取回的候选按 ER-05 规范化后确认级别。
3. **排序与截断**：最高级别内按命中值长度、实例键排序，最多展示 `limit` 条；超过时 `truncated: true`，状态不受影响。
4. **定状态**：按 ER-03、ER-10。

没有标题属性、也没有业务标识属性的实体类型返回 `NOT_RESOLVABLE`，提示先在模型中设置标题属性或业务标识。

## 4. 输出

```json
{
  "workspace_id": "…", "version_id": "…",
  "mention": "星河电子",
  "object_type_id": "…",
  "status": "AMBIGUOUS",
  "truncated": false,
  "candidates": [
    {"source": "database", "entity_ref": "…", "display": "星河电子有限公司", "match": {"level": "name_contains", "property_id": "…", "value": "星河电子有限公司"}, "identifiers": {"supplier_code": "SUP-1001"}},
    {"source": "database", "entity_ref": "…", "display": "星河电子终端有限公司", "match": {"level": "name_contains", "property_id": "…", "value": "星河电子终端有限公司"}, "identifiers": {"supplier_code": "SUP-1002"}}
  ]
}
```

- `entity_ref` 沿用现有实例引用格式（数据库实例为类型 id + 业务键，文档实例为实例 UUID），后续查询直接使用，不再按名称匹配。
- `identifiers` 给出业务标识属性的值，便于追问时让用户区分。

## 5. 与其他能力的衔接

- `search_ontology` 返回的 `unmatched_terms` 由 semantic-grounding Skill 判断哪些是实体提及，再调用 `resolve_entity`。
- entity-extraction 写实例前可调用它检查是否已有同一实例：文档实例命中可提出对已有实例的更新提案，业务库命中只作说明（ER-11）；最终是否同一实体由人工审阅决定。
- 工具随路线图步骤 5 上线；在此之前 Skill 和提示词不得调用 `resolve_entity`。

## 6. 验收

- 虚构采购协同领域：同前缀多家供应商、唯一包含命中、业务编码精确命中、复合标识完整与部分给出、截断位置之后仍有同级命中、全角源值、未找到、无标题属性的类型。
- 权限：无实例权限时拒绝；业务库只读查询经现有白名单。
- 问数 Agent 遇到 `AMBIGUOUS` 时追问而不是任选其一。

## 7. 不做

- 不对实例做向量化，不做跨来源实体合并，不输出置信度。
- 不新增别名、曾用名等模型概念；数据中已有并映射为属性的列，可在后续版本加入匹配范围。

## 8. 实施结果

- 服务 `services/entity_resolution.py`；MCP 工具 `resolve_entity` 与 REST `POST /api/v1/ontology/workspaces/{workspace_id}/entities/resolve` 共用。
- 业务库候选复用现有只读实例查询（`instance_plan.query_instances`，含映射、权限与白名单），以“包含”取最多 200 条（同时尝试输入原样与 NFKC 写法），在 Python 中按 ①②③ 判级；精确命中必然也是包含命中，因此候选不遗漏。读取被截断时状态不判为 `MATCHED`，`coverage` 为 `partial`（ER-10、ER-12）。
- 文档实例取 `instance_store.visible`（按所用版本过滤不兼容实例），类型含子类型。
- 复合业务标识不参与 ① 级；无标题属性且无单一业务标识的类型返回 422 `NOT_RESOLVABLE`；无实例权限 403。
- semantic-grounding 与 entity-extraction 技能已写入调用方法；插件清单工具列表加入 `resolve_entity`。
- 测试：`apps/api/tests/test_entity_resolution.py`（文档实例分级与状态、全角规范化、MCP 与 REST 一致、业务标识精确命中、截断不判唯一、未知类型）。
