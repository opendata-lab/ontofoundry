# 只有接口、没有数据表的业务数据

日期：2026-11-27。状态：调研结论已确认，首版不改模型。

同类产品调研由 Codex gpt-6.2-sol 完成，记录在 `~/.agents/handoffs/2026-11-27-codex-api-source-survey/`（不入库）。

## 1. 问题

本体对象类型映射到数据集，数据集现在只有 `table` 和 `query` 两种来源（[数据集来源](2026-10-20-dataset-sources.md)），查询 Agent 用只读 SQL 取数。有些业务系统只开放 HTTP 接口或 MCP 工具，没有可读的表。

[语义层](2026-11-11-runtime-agnostic-semantic-layer-for-agents.md)初稿（SL-13）曾设想过两种做法：
- 数据集增加 `source_kind: api | mcp_tool`；
- 属性直接绑定接口返回值，例如 `Customer.live_credit_score`。

11-12 修订时，这两种做法都移到了“未确认”。

## 2. 同类产品

| 做法 | 产品 | 要点 |
|---|---|---|
| 读取时实时调接口 | Dataverse 虚拟表、Salesforce Connect 外部对象、ServiceNow Remote Tables、Denodo、Steampipe、Trino 连接器 | 先把接口结果声明成带键、有类型的表和列，上层再查询。只有声明过的条件能下推到接口，例如 OData 的过滤、分页，或 Steampipe 的键列；跨表连接和聚合要么由引擎在本地做，要么受限，例如 Salesforce 一次最多连接 4 个对象，Dataverse、ServiceNow 默认最多 1000 行 |
| 按实体键补字段 | Palantir Workshop 函数列、Hasura Remote Schema、Apollo Connectors | 打开对象或返回一页结果时，按键调用接口补字段；不作为全量筛选或指标的输入 |
| 先落表，本体只认表 | Palantir Foundry、Fabric IQ、SAP Datasphere（通用 HTTP）、Cube、dbt 语义层 | 接口数据先同步成数据集或表，再映射。Foundry 的 REST 来源只用于交互式调用，不能直接同步；Fabric IQ 的本体只能绑定 Fabric 数据项的列 |

各家分工一致：模型里放键、字段含义、关系和度量；端点、认证、分页、限流和缓存放在连接器或运行配置里。

## 3. 结论

**首版：接口数据先落表，模型不改。**
- 由数据平台的同步任务调用接口，写进独立的目标表，并在那里处理分页、增量、去重和更新。表里要有稳定的键和列，并写明数据截至时间。
- 落表之后按现有方式建数据集和映射，实例、指标、问数和 MCP 都直接沿用。
- 暂时不能落表的对象类型，照常定义但不做映射，在说明里写明数据来自哪个系统。外部 Agent 读到说明后，就知道要改用自己接入的业务系统工具。

**以后有具体需求时，再从下面两种里选一种，各自单独写设计：**

| 做法 | 适合 | 边界 |
|---|---|---|
| 数据集 `source_kind: api` | 接口能稳定返回带键的行集，而且业务要求实时，或者不允许复制。例如按仓库和业务日期查当天的作业任务 | 数据集引用连接里登记的一个读取操作，并声明输出列；属性照常映射到这些列。接口地址、认证、分页、限流和缓存放在连接配置里，不放进模型。首批只承诺按键和受支持的条件读取、分页和预览；跨源 SQL、全量聚合和 SQL 参考，要各自有执行路径后才提供。`mcp_tool` 只作为连接器的一种实现方式，前提是工具输出的结构稳定、有记录键、读取参数明确 |
| 属性按键实时补值 | 对象已经有表和主键，只需要补少量当前值。例如打开运单详情时，按 `shipment_id` 查“当前承运状态” | 只用于详情或明确的按键读取，不作为全量筛选、排序或指标的输入。支持批量取键时，要避免逐行发请求 |

两种做法都需要在核心设计 §7 的 Ossie 例外表登记导出时怎么表示。

## 4. 开工前要回答的问题

| 问题 | 例子 | 倾向 |
|---|---|---|
| 允许复制吗，数据最多能旧多久？ | 仓库看板 10:00 读 09:45 的快照，和调度员 10:00 打开运单要看源端当时的状态，是两种不同的承诺 | 聚合看板用写明截至时间的副本；只有确实需要最新值的单个对象，才实时取 |
| 首版要回答哪类问题？ | “运单 A123 现在什么状态”只需要一次按键查询；“筛出全部滞留运单、按仓库算比例”需要完整行集、筛选和聚合 | 需要第二种就落表。如果规定不允许复制，先逐项核对接口的筛选、分页和完整性保证 |
| 用谁的身份读，失败时怎么显示？ | 源系统只给一个服务账号，但调度员甲只能看东仓、乙只能看西仓；限流导致第 2 页没取到 | 按源端权限决定用每个用户自己的身份，还是服务账号加平台侧的权限约束；缓存按实际权限隔离；结果不完整时，实例显示暂不可用，精确指标直接报失败 |

## 5. 已确认决定

| # | 决定 | 来源 |
|---|---|---|
| 1 | 首版接口数据先落表，数据集仍只有 `table`、`query` 两种来源 | 用户 2026-11-27 |
| 2 | 不采用“以接口为常态来源、数仓表作补充”的定位（SL-13、SL-14 初稿） | 同类产品调研：本体和语义层普遍只认表或类表结构 |
| 3 | 接口地址、认证、分页、限流、缓存不进入模型；以后增加 `api` 数据集时放在连接配置里 | AGENTS.md 产品原则；各产品的分工 |
