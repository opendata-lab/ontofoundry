# 大型结构化材料的建模：摘要、续做与早落盘

日期：2026-11-18。状态：已实施并验证（设计评审 Codex gpt-6.2-sol，实现评审 Gemini 4 Argon，记录在 `~/.agents/handoffs/2026-11-18-*large-material*`）。来源：用户 2026-11-18 提供的内网会话记录（架构治理场景，`~/Downloads/arch-gov-modeling-session-*`，不入库），以及用户的判断：“原来有完整本体，要求重新建模也不过分”。

## 1. 问题

### 1.1 这次发生了什么

| 项 | 数据 |
|---|---|
| 材料 | `architecture-governance.ossie.json`，Apache Ossie 0.2，10,294 行：29 个概念、语义模型 41 个数据集、14 条数据集连接、27 个指标、`concept_mappings` |
| 关联表 | 276 张，表结构文件 29,374 行；最终只用到 41 张，其余约 235 张是 `deprecated_*`、`_bak`、`_123`、`test_` 等废弃、备份或测试表 |
| 运行 | 9 次，跨两天；5 次 `PI_RUN_TIMEOUT`（单轮约 30–40 分钟），1 次 DataAgent `database is locked` |
| 前 8 次 | 没有一次往 `modeling/parts/` 写过片段 |
| 第 9 次 | 用户问“不是抽过了吗 能复用吗”，智能体读 `modeling/tmp/digest.json`，21 分钟交出 29 概念、41 数据集、27 指标 |

### 1.2 原因

1. **结构化材料没有按结构读成。** 2026-11-06 已确认“结构化文件由工具解析、渲染为可读单元，智能体只读小份可读文本”（`2026-11-06-table-scope-and-ai-ready-reads.md` T3、T4），`read_input.py` 也有 `--outline`、`--pointer`。但对这份大而嵌套的 JSON：大纲对数组只给第一项作“示例”，压成一整行，看不到 29 个概念各是什么、各在哪几行；`--pointer /ontology` 吐出原始 JSON 文本，不是可读单元。智能体只好 `grep '"concept"'` 原始行，再按行号分页把整份拼回来（前三次运行 46、35、38 个回合都耗在这里；工具调用几乎都不到 1 秒，每个回合约 40 秒花在模型生成上）。第 6 次运行它自己写了 `make_digest.py` 做摘要，第 9 次用摘要 21 分钟完成。
2. **续做不认中间成果。** 初始化只把 `parts/`、`checks/`、`plan.md`、`notes.md`、`entities.json`、`issues.json` 当作成果（`init_workflow.WORK_FILES`）；`modeling/tmp/` 不在其中，续做摘要也不列它。所以每次都打印 `PLAN_KEPT … 尚未写片段`，智能体从头再读。
3. **先读完再写。** 抽取步骤没有要求尽早写出 `entities.json` 和首批片段；超时就什么都没留下，续做也只能走“计划已保留”的路径。
4. **表范围过大。** 276 张表中大部分明显是废弃、备份或测试表，每次运行都为它们多读一遍表清单和表结构。

重新建模是合理需求，问题在于平台没有为“大型结构化材料”提供合适的读法，也没有让超时后的成果可续用。

## 2. 目标与非目标

目标：同类材料（数千到上万行的本体或语义模型文件、上百张关联表）在**一次运行内**完成全量建模；超时后的下一次运行**不重读材料**。

非目标：
- 不调大 DataAgent 单轮超时（那是部署配置，可另行调整，不解决根因）。
- 不让用户在“导入”和“重新建模”之间选择，也不加新的计划选项（用户 2026-11-18：简单为好，不增加心智负担）。
- 不改核心模型；只涉及运行输入、技能脚本和步骤文字。

## 3. 已确认决定

| 编号 | 决定 | 来源与理由 |
|---|---|---|
| LM-01 | **把 JSON 的结构化读法做对（落实 T3、T4），不做格式专用摘要。** `read_input.py` 的 JSON 视图改为：**大纲**对数组逐项列出每个元素一行——路径、原文行号、名称类字段（`name`、`concept`、`id`、`title` 等中先出现的），超出单次上限时分页并给出下一页命令；**按路径读**把对象渲染成“字段: 值”每行一项的可读单元，嵌套的对象数组只列各元素名称和子路径，超长值截断并给出读全文的命令，原文行号照常标在每行；`--pointer` 可一次给多个路径。单次输出仍不超过 8000 字节。任何结构化 JSON 都适用，不识别具体格式。 | 落实已确认的 T3、T4，读取器本来就在技能里（读材料不是平台规则）。行号由读取器按原文计算（`JsonSource`），可直接写证据。删掉的后果：大型 JSON 只能按原文行读，即这次的情况。 |
| LM-02 | **续做认中间成果，清单只有一份。** 初始化（`init_workflow.WORK_FILES`）和提交后归档（`prepare_result.archive_submitted`）共用同一份成果清单，加入 `modeling/tmp/`：基线未变、未入库时保留，基线变化、`--restart` 或已入库时一起归档。`PLAN_KEPT` 也打印续做摘要（现在只有 `PREVIOUS_WORK_KEPT` 打印），列出 `entities.json`、已写片段和 `tmp/` 里的文件名；`resume.md` 写明先用已有结果，不重读材料，必要时按 notes 里的“已完成／待补”只补缺的部分。`PLAN_KEPT` 不代表计划已批准，仍按现有计划门禁。 | 修正现有续做（MR-01、MR-02）的遗漏：现在 `tmp/` 既不保留也不归档，跨轮残留；续做提示不提它，智能体每次重读材料。 |
| LM-03 | **技能文字：结构化材料按结构读，早落盘，自行判断。** 抽取和计划步骤写明：JSON、CSV 等结构化材料先看大纲、按路径读可读单元，不按行号分页读原文；范围定下后先写 `entities.json` 和首批片段，`notes.md` 记“已完成／待补／有意为空”。计划步骤补两句：材料是完整本体时，照着材料建还是按表调整由智能体判断，不问用户；关联表很多时，在计划里列出并排除明显废弃、备份、测试的表。 | 只改步骤文字，不加脚本或选项。 |
| LM-04 | **`expand_tables.py` 认每日快照表（2026-11-24）。** `entities.json` 的实体可写 `snapshot_date_column`：该列写到生成的表数据集上，从实体标识、映射 `key_columns` 和生成的属性中去掉，标识用主键的其余列；同表多个实体的声明必须一致。脚本只查该列在表里，类型由平台按数据集规则校验（日期、日期时间、可排序的文本或整数）。 | 落实已有决定：快照只在 `Dataset.snapshot_date_column` 上声明，选定日期后实例关联键仍用实体键（`2026-10-14-core-model-and-format-adapters.md` §3.7“数据集快照与关联提示”）。原脚本把物理主键全部设为标识且不许排除，快照表的实体都多出一个日期标识，关系对不上（§7）。不加新字段到核心模型。 |
| LM-05 | **抽取步骤去掉三处已证实的空转（2026-11-24）。** `--extract 1`、`--extract 2` 分两次调用，不用 `&&` 合并；`--variant` 直接列出全部名称；查到的 t# 与 connection_id 记进 notes.md；套不进清单的实体直接写 01b、03b 落盘，不为它反复改 `entities.json`。 | 只改步骤和写法包文字。都是工具用法和落盘顺序，不针对某类业务语义。 |

## 4. 不采用的方案

- **平台为 Ossie 材料生成专用摘要**（评审稿的 LM-01）：只对一种格式有效，要平台识别格式、加工作包字段、另算原文行号；通用的结构化读法做对后不需要。用户 2026-11-18：结构化文件用结构化读法，非结构化用非结构化读法。
- **在计划卡片上加“从导入开始，再修订”的选项**：用户 2026-11-18 否决，增加心智负担；改为智能体自行判断（LM-03）。
- **平台把导入结果改写成候选片段放进运行输入**：省掉手写，但要把带 UUID 的导入结果改写成 `client_ref` 片段、标出待补全，新机制太多；有了摘要，照着材料写已经很快（这次第 9 次运行 21 分钟）。
- **用脚本按命名规则标出疑似废弃表**：规则在别的客户库里会误判；由智能体在计划里判断并列出（LM-03）。
- **只调大单轮超时**：治标；同样的读法换成 60 分钟也只是多读一些。

## 5. 验证

- **冷启动样本，接近原规模**：用平台导出一份虚构本体为 Ossie 文件（保留嵌套映射和复杂指标），关联它引用的表，再加约 100 张 `deprecated_`、`_bak`、`test_` 命名的虚构干扰表，发起全量建模，不预置任何中间成果。
- **指标**：是否一次运行完成；到第一份片段落盘的时间；读原文、读表结构的调用次数与字节数；回合数、输出 token；入库结果是否完整。计划等待时间和 DataAgent 自身错误（如 `database is locked`）单独计。
- **续做**：分别在首批片段之前、以及一类片段写到一半时取消运行，再发“继续”，确认跳过已完成的部分、识别待补项、最终完整入库。
- **回归**：星河、青禾两个现有场景的轮数与修正次数不变差。

## 5.1 验证结果（2026-11-18，:8902，deepseek-flash，记录在 `~/.agents/handoffs/2026-11-18-claude-large-material-verify/`）

| 场景 | 结果 |
|---|---|
| 冷启动：10,945 行 Ossie 材料（平台导出的虚构青禾本体，54 个概念），136 张表（102 张干扰表） | 一轮完成：计划 21 回合 81 秒，抽取 35 回合 156 秒；读材料用大纲 3 次、按路径 11 次，没有按行号分页；411 条提案一次全部接受；37 个数据集无一绑到干扰表；约 ¥0.04 |
| 进入抽取、写片段前取消，再“继续” | 打印 `PLAN_KEPT`，按抽取步骤继续；重新读材料（取消前没写下任何东西，属必要）；一轮完成，36 回合 165 秒，一次提交、零修正 |
| `expand_tables.py` 写出 01–03 后取消，再“继续” | 打印 `PREVIOUS_WORK_KEPT`，走续做步骤；完整入库（32 回合 153 秒，零修正），但把示例、表结构和材料又读了一遍并重新生成 01–03，没有只补 03b、04 |

对比内网原始情况（5 次超时、前 8 次运行没写出片段），LM-01 解决了主因。已知局限：取消前读到的内容只在模型上下文里，续做时只能重读；由于整轮已缩短到几分钟，不再为此加机制。条件差异：材料由平台导出、结构规整，表有主键，模型为 deepseek-flash，耗时不能直接当作内网预期。

## 6. 评审结论（2026-11-18）

Codex 9 条意见：采纳 8 条，并入 LM-02、LM-03 和验证；1 条（保留导入选项）不采纳，用户已否决。评审之后，用户指出应沿用“结构化文件用结构化读法”的原则，LM-01 由 Ossie 专用摘要改为把通用 JSON 读法做对；Codex 关于摘要上传、格式识别和平台侧行号的意见随之不再适用，关于单次上限和续页命令的意见（第 1 条）并入新的 LM-01。
