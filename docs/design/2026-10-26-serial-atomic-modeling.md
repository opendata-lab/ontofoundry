# 建模串行化与原子化

日期：2026-10-26。状态：已确认（用户 2026-10-26），实施计划见 `docs/plans/2026-10-26-serial-atomic-modeling-plan.md`。

本设计取代以下内容：

- `2026-10-23-proposal-checks-in-conversation.md` 的 CK-02（入库时逐组放行）；
- `2026-10-26-checks-before-output.md` 的 CO-02（`--drop-unacceptable`）；
- 其他文档中“新批次取代旧待审提案”的做法。

## 1. 问题

“检查”和“接受”不在同一时刻进行，看到的草稿也不同：

- 检查用的是运行开始时固定下来的草稿；
- 接受用的是用户点按钮那一刻的草稿。

两者之间，可能有别的批次被接受、草稿被编辑，或者新一轮运行开始。为了应对这些情况，系统逐渐加上了：

- 新的状态：不可接受、已变化、冲突、被取代；
- 补救路径：修复任务、去掉不可接受组、跨批次查重；
- 两套规则：检查一套，接受时又多出几条，例如数据集来源、证据归属、身份种类。

## 2. 保证范围

在固定输入和本会话状态不变的前提下，检查通过的一批提案入库时，不会因为规则遗漏被拒收；逐条接受时，只要按依赖组接受，也不会因为规则遗漏失败。

以下情况属于边界情况，只报错，不另行设计：

- 外部数据源连通性或业务库的变化；
- 其他会话并发修改共享实例；
- 基础设施故障。

## 3. 已确认决定

| 编号 | 决定 |
|---|---|
| SA-01 | **串行化。** 会话“被占用”指：运行在进行中（提交中、排队、运行、等待回答、等待批准），或者运行已结束但结果还没处理完。<br>· 占用期间，不能发起新一轮，不能编辑草稿，不能接受、拒绝、修订提案。<br>· 本会话还有待审提案时，不能发起新一轮建模，也不能直接编辑草稿（元素保存、合并、导入覆盖都算）。要改就先处理完待审提案，或在提案上修订。<br>· 检查在服务层用短事务门禁完成，不持有跨运行的长锁。界面只做提示。 |
| SA-02 | **一套规则、一个入口。** 平台提供一个共享的“试应用”入口：输入一批提案（来自 Agent 原始结果、导入，或已存的待审批次加上修改），在当前草稿上做完整校验，输出规范化后的候选结果，不持久化。<br>覆盖：契约、引用和 before/hash、整图校验（含英文标识唯一）、数据集来源的静态校验（属于本空间、表已登记、SQL 白名单）、证据哈希、行号、原文和归属（包括同一批内是否复用证据 id）、身份种类、实例 revision 和目标状态。<br>· 运行内的检查接口、结果入库、提案修订、导入、接受，全部调用它；<br>· 接受时，对所选提案和它的依赖闭包调用它，再在同一事务中写入；<br>· 实时连接探测（例如查询型数据集用 `LIMIT 0` 试连）不作为门槛，只在预览或查询时报告。 |
| SA-03 | **整批原子。** 检查和入库要么整批通过，要么整批不通过。<br>· 不通过时，Agent 在运行内修正，最多两轮；仍不通过就不交结果，并在回答中说明。<br>· 入库时，批次、提案项、依赖关系和结果状态在同一事务中写入；入库失败则不建批次。<br>· 合并脚本只能在平台检查通过后写最终结果：缺少检查配置时报错；删除 `check_result.py --publish`；删除 `--drop-unacceptable`。 |
| SA-04 | **逐条审阅，按组决定。** 提案状态只有待审、已接受、已拒绝三种。<br>· 依赖关系，以及必须一起决定的组（英文标识互换、复合标识等），由试应用推导出来。<br>· 接受时，连同待审的依赖一起接受；拒绝时，连同依赖它的待审提案和同组提案一起拒绝；撤销已接受的提案时，同时处理已接受的依赖者。<br>· 修订提案内容后，整批重新试应用，通过才保存。 |
| SA-05 | **旧批次只读。** 新一轮运行开始后，之前批次的决定不能再恢复或撤销。 |
| SA-06 | **对话只属于 DataAgent。** 事件流和对话快照都只做透传、鉴权和凭据脱敏，不处理结果，也不改写运行状态。<br>运行生命周期（提交状态未知时的对账、任务替换、结果处理）放在建模运行服务中，由读会话等入口幂等触发。对话中的运行状态就是 DataAgent 的状态；结果的处理情况由提案面板显示。 |
| SA-07 | **导入。** 首次导入接入 SA-02 的试应用。导入报告补全时，在当前待审批次内更新候选内容和依赖关系，不再生成新批次去取代旧的；修订实例事实（`revise_fact`）也在当前批次内进行。 |

来源：SA-01～07 都是运行协议和审阅流程，不进入本体模型。

## 4. 删除

- 存储的状态 `unacceptable`、`superseded`，推导出的状态 `stale`、`conflict`，以及相关的判定、页签、文案和测试；
- 入库时逐组放行、跳过不合法组的逻辑；
- `store_failed_batch`：入库失败不再建批次；
- `--drop-unacceptable`、`check_result.py --publish`，以及缺少配置时跳过平台检查的分支；
- 对话快照中的结果处理和运行状态改写；
- 新批次取代旧待审提案的做法（`store_batch`、导入补全、`revise_fact` 中都有）。

## 5. 保留

- 提案的待审、已接受、已拒绝三种状态；
- 结果处理状态（processing、done、failed_retriable、failed_permanent），以及结果租约、幂等、迟到任务隔离；
- 实例的 staged、active、deleted 三种状态，以及实例 revision 的比较后写入；
- 发布时的合并冲突保护；
- 运行内修正计数，以及计划卡片、问题卡片。

## 6. 锁的释放

| 情况 | 行为 |
|---|---|
| 运行明确失败 | 记录终态，释放占用，不建批次 |
| 用户取消 | 确认取消后释放；这一代运行的结果作废，迟到也不入库 |
| 任务已结束、结果还没处理 | 保持占用，直到处理成功或明确失败 |
| 下载暂时失败 | 重试期间保持占用；重试用完后，结果标为失败并释放 |
| 平台重启 | 占用状态已持久化；结果租约过期后，可由其他请求接管 |
| 提交状态未知 | 由运行服务对账；超时后标为失败并释放 |
