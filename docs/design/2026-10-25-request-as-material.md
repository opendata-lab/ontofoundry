# 对话建模需求保存为材料

## 背景与边界

只有对话描述、没有上传材料或数据表时，实例仍必须有证据；原有“引用材料”和“用户担保（作者由服务端写入）”不能让 Agent 引用聊天描述，导致抽取轮耗尽而没有结果。采用用户已确认的方案 A：平台将建模需求原文保存为工作空间材料，复用材料证据，不增加第三种证据。

## 已确认决定

推荐值作为本次实现默认值；待确认项不影响已确认方案 A 的落地。

## 新增值的依据

`conversation_request` 是平台自创的材料来源分类，属于输入溯源元数据，不是业务语义或查询执行优化；Ossie、Fabric IQ、Foundry 均不是该枚举值的直接来源。删除后仍能引用材料，但无法在材料列表区分自动保存的对话需求。现有 `upload` 与 `table_receipt` 无法准确表达该来源。复用现有材料、分块、会话材料 id 与材料证据，不新增业务模型字段、状态或证据模式。

## 运行流程与契约

服务层判断消息是否满足保存规则，调用共享文本材料存储。路由将返回材料加入本轮输入，并在带 revision 和运行状态校验的事务中更新会话 `material_ids`。保存原文分块和源文件，沿用恢复能力及上传路径；提案模式的工作包通过现有材料索引提供 `id`、`path`、`lines`、`original_range`、`sha256`，后续确认、重试和抽取轮继续携带。

材料 Pydantic 与生成的 JSON Schema、前端类型同步接受来源值。数据库 `origin` 已是长度 20 的字符串，`conversation_request` 为 20 字符，现有唯一约束不变，无表结构变化、无 Alembic 迁移、无历史数据迁移。

## 改前改后例子

虚构工作空间“云杉协作”没有材料和表，用户发送：

```markdown
云杉维修站管理维修工单。
工单 WX-101 已由小岚接单，预计明日完工。
```

改前：计划轮可以识别“工单”“员工”，抽取轮无法给 WX-101 和小岚提供材料证据。

改后：平台保存完整原文为 `建模需求-2026-10-25-1646.md`，来源“对话需求”。工作包列出真实路径、2 行和原文 SHA256；Agent 可引用第 2 行作为工单和员工实例的证据。是否成立、是否只是计划仍由技能按原文判断，自动保存不等于用户担保。

用户随后发送“确认”或“重试”：不增加材料，继续携带已有需求。重复发送完全相同的长消息：复用同一材料 id；原文加空格或修改换行会改变 SHA256。查询模式下发送相同描述：不自动保存。

## 配套展示与技能修正

- 通知读模型增加可空的 `batch_id`，由既有本轮批次关联派生，不持久化；不能用会话的历史最新批次判断本轮。本轮没有提案批次时，失败平台消息只显示原因与“重试”，不显示零计数；有批次继续显示统计。
- 工具记录仅在展示投影中规整路径，原始记录不变：技能根下显示“技能 <名称>/相对路径”，工作区的 uploads/output/modeling 等目录保留相对路径；其他本机绝对路径仅展示文件名。不修改下载路径、工具调用参数或用户、Agent 正文。
- ontology-discovery 与 entity-extraction 的步骤明确 `extract-facts.md` 在实例抽取技能 entity-extraction 下；工作包示例索引同步指明归属。
- 复用既有 Alert、Select、Table，不新增布局模式和视觉变量；1440×900 对比按视觉一致性设计第 3 节核验。
