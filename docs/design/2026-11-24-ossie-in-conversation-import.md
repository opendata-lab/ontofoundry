# 建模对话中的 Ossie 材料：运行前导入为待审提案

日期：2026-11-24，2026-11-25 重写。状态：用户已确认方向，待实施。来源：内网大型 Ossie 材料重放（`2026-11-18-large-material-modeling.md` §7）；用户 2026-11-19“在对话里识别到是 Ossie 后用脚本处理导入”；Ossie 导入修复 PR #106、#107、#109。

本文替代本文件的前一版（“智能体调脚本、平台接口返回片段”，见 git 历史）。前一版经 Codex、Gemini Neon 两轮设计评审和一轮计划评审，记录在 `~/.agents/handoffs/2026-11-24-codex-ossie-in-conversation-review/`、`2026-11-24-neon-ossie-in-conversation-review/`、`2026-11-25-codex-ossie-in-conversation-plan-review/`。用户 2026-11-25 逐项审视复杂度后改为本方案，理由见 §6。

## 1. 问题

在建模对话里上传大型 Ossie 材料时，智能体只能逐段阅读、手写片段。内网一万行的材料每回合 63–109 秒，40 分钟只有约 22–38 回合，多次超时。

导入器（#106、#107、#109 之后）已能确定性地转换这份材料的大部分内容：error 20 → 2，对象映射 11 → 21。但构建页“导入文件”不在对话里，结果落在新会话中；纯 Ossie 材料也接不上已登记的表。

## 2. 做法

```
用户在对话里带上 Ossie 材料发消息
→ 平台识别出 Ossie，用导入器转换（按本会话的表接连接）
→ 转换结果作为本会话的待审提案
→ 运行开始：固定的草稿已包含这些提案，工作包带上转换报告摘要
→ 智能体补报告里的缺口、判断快照列和未证明的连接、润色显示名，然后提交
→ 与导入提案合并成一个待审批次（AI-08）→ 用户审阅一次
```

1. **识别与触发（用户 2026-11-25 选：发消息时自动）。** 建模运行开始前，平台检查本轮材料：能被 `OssieAdapter.detect` 识别的单个 JSON 材料即导入。同一会话中同一材料（按 SHA）只导入一次，之后的运行不再导入。ZIP 交换包仍走“导入文件”（材料存储只收文本）。
2. **转换。** 与“导入文件”使用同一个导入器。`ImportContext` 带本会话本轮固定的表清单（`table_snapshot`）：
   - **按表名接连接**：数据集 `source` 为 `schema.table`，本会话的表中恰好一张同 schema 同表名的登记表时，采用其连接；没有则数据集不接连接，报告“缺表”。扩展文件里有连接名时仍以扩展为准。“导入文件”路径不传会话表清单，行为不变。
   - **只要求非空的约束转为属性必填**：`requires` 只要求某属性不为空（如 `order.code IS NOT NULL`）时，等价于该属性必填，设 `required=true`、不生成规则（对话提交会拒绝这类规则，`proposal_apply._no_required_rules`）。
   - 其余不确定的不处理，留给智能体：物理连接目标未声明唯一键的、快照列、本体标识与表主键的差异。
3. **落为本会话的待审提案。** 复用“导入文件”生成提案的逻辑（`build_candidate_graph`、`build_import_batch`、`check_proposal`、`store_batch`，见 `services/imports.py` `confirm_import`），差别只在：基线是本会话草稿而不是已发布版本；不新建会话；本会话已有待审提案时，按 AI-08 合并为一个待审批次。批次来源记为导入（`producer.kind = import`），与“导入文件”一致。
4. **运行输入。** 运行固定的草稿是“会话草稿加上待审提案”（现有，`api/agent_conversation.py`、AI-05），智能体看到的导入元素带真实 UUID，可以引用、修改、删除。工作包加一项 `import_report`：报告摘要（≤ 8 KB：转换条数、缺表、待补全、未证明的物理连接及两端登记表主键），明细另存文件按需读。
5. **智能体做什么。** 按技能参考页（§4）：读报告；为报告列出的数据集判断快照列，依据写进提案 `reason`；判断未证明的物理连接，成立的写关系对接；补其他待补全项；润色显示名和描述。不重复建导入已有的对象（它们已在草稿里）。
6. **提交与审阅。** 提交时智能体的结果与导入提案合并（AI-08）：改过的导入项仍是一条新增提案，内容是改后的；没提到的原样带入。用户只审一个批次。

## 3. 例子（虚构）

材料：`order` 映射自 `sales.order_df`，`customer` 映射自 `sales.customer_df`，物理连接 `order_df.customer_no → customer_df.customer_no`。本会话关联了这两张表，登记主键分别是 `(order_no, ds)`、`(customer_no, ds)`。

| | 现在（对话） | 按本设计 |
|---|---|---|
| 读材料 | 智能体逐段读、手写片段 | 运行前平台一次转换为待审提案 |
| 数据集连接 | 智能体逐个配 | 按 `sales.order_df` 在本会话表中唯一匹配 |
| 订单 → 客户连接 | 智能体判断 | 报告列为未证明，附 `customer_df` 主键 `(customer_no, ds)`；智能体判断 `ds` 是快照列、连接成立后写关系对接 |
| 显示名 | 智能体写 | 导入只有英文名，智能体改成中文，与导入提案合并 |
| 审阅 | 一批 | 一批 |

## 4. 改动范围

- **导入器**：按会话表清单接连接；只要求非空的约束转为属性必填；报告附未证明物理连接两端的登记主键。
- **平台**：运行开始前识别并导入（放在解析会话表范围之后、计算待审上下文之前）；导入落到当前会话并与待审提案合并；工作包加 `import_report`。
- **技能**：`import-completion.md` 现在写的是“当前阶段不提供导入执行工具，已有报告只是待分析材料”，改为说明本会话有导入提案时怎么读报告、可以修改导入项、快照列和未证明连接由智能体判断并写依据。`plan.md`、`extract.md` 不增字节；计划模式下导入提案已在待审中，计划只需说明“补全导入缺口”。
- 不改核心模型、提交入口、合并逻辑、表展开脚本。

## 6. 为什么不用前一版

前一版让智能体在运行中调脚本、平台返回片段文件。为此需要：新的平台接口和运行凭据扩展、把导入结果序列化成智能体格式、按实体拆文件、哈希清单和 `--force`、表展开跳过已导入对象、计划阶段的 `--inspect`。

这些复杂度都来自“导入结果交给智能体在运行中编辑”。现有机制已经覆盖这个需求：运行固定的草稿包含待审提案（AI-05），提交时与待审提案合并成一个批次（AI-08）。只要导入发生在运行开始之前，智能体就能直接引用和修改导入的元素，上述机制都不需要。

## 7. 待实施时核实

- 运行开始前导入失败（材料不是合法 Ossie、转换出错）时：报告进工作包，运行照常开始，智能体按普通材料阅读，不阻断对话。
- 导入批次与已有待审批次合并时，同一目标冲突（用户手工提案与导入提案改同一元素）按 AI-08 处理是否合适。
- 导入提案的证据定位到已登记材料的原始行（“导入文件”路径已有 `source_evidence`，核对对话材料能否复用）。
- 导入提案数量很大时（这份材料约 350 条），工作包元素索引分页（现有）和智能体回读的开销。
