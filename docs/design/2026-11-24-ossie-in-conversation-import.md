# 建模对话中的 Ossie 材料：确定性导入并接到已登记的表

日期：2026-11-24。状态：已评审（Codex，§8），用户决定见 §4、§9；待写实施计划。来源：内网大型 Ossie 材料重放（`2026-11-18-large-material-modeling.md` §7）；用户 2026-11-19“在对话里识别到是 Ossie 后用脚本处理导入”；Ossie 导入修复 PR #106、#107、#109。

## 1. 问题

平台已有两条路径：

| 路径 | 做法 | 问题 |
|---|---|---|
| 构建页“导入文件”（P4，`2026-10-18-core1-p4-import-workflow.md`） | 导入器确定性转换，生成新会话和一批待审提案 | 用户在建模对话里上传 Ossie 材料时不会走这里；连接只认扩展文件里的连接名，纯 Ossie 的数据集都连不上 |
| 建模对话 | 智能体逐段阅读材料，手写片段 | 一万行材料要读几十个回合，内网多次超时（每回合 63–109 秒，40 分钟约 22–38 回合） |

#106、#107、#109 之后，导入器对那份材料已能转换全部 29 个概念中可表达的部分：error 20 → 2，对象映射 11 → 21。剩下的主要缺口都和“接到真实的表”有关：

| 缺口 | 数量 | 原因 |
|---|---|---|
| 数据集没有连接 | 41 / 41 | 纯 Ossie 没有连接信息 |
| 物理连接未证明 | 14 / 14 | 材料没写目标表的唯一键 |
| 快照列 | 0 / 41 | 纯 Ossie 没有快照概念 |

## 2. 目标与非目标

目标：对话里出现 Ossie 材料时，可确定转换的部分由导入器一次完成，智能体只处理转换报告里的待补全项和需要业务判断的问题。

非目标：不改核心模型；不从描述或列名猜业务含义；不替用户修材料中的建模问题（见 RI-06）。

## 3. 做法

```
智能体识别到 Ossie 材料
  → 按工作包里的表清单判断哪些表是每日快照、快照列是哪一列，写进 notes 并说明依据
  → 运行脚本 import_ossie.py --snapshot 表=列 …（用本轮运行凭据调用平台，只调用一次）
      平台：导入器转换，按表名接连接，设快照列，用“登记主键去掉快照列”证明物理连接，返回转换结果 + 报告
      脚本：结果按元素写成 modeling/parts/00-ossie-*.json，报告写成 modeling/checks/ossie-report.md
  → 智能体读报告，只处理待补全项
  → 照常合并、提交；用户在审阅提案时确认
```

1. **识别**：智能体按材料内容判断是 Ossie（顶层有 `ontology`，或是 Ossie 交换包），技能步骤文字写明“遇到 Ossie 材料先运行 `import_ossie.py`，不逐段阅读”。脚本把文件交给平台，由 `OssieAdapter.detect` 最终确认，不是 Ossie 就报错退出，智能体回到普通阅读。
2. **转换（平台）**：新增按运行凭据访问的接口，与提交检查使用同一份 `platform_check_file` 凭据。平台用与“导入文件”相同的导入器转换，`ImportContext` 带上本会话关联的表，以及工作空间的连接和登记表。只返回结果，不建会话、不建提案、不改草稿。
3. **按表名接连接**：数据集 `source` 写成 `schema.table` 时，在本会话关联的表中找同 schema、同表名的登记表，恰好一张就采用它的连接。扩展文件里有连接名时仍以扩展为准。规则见 §4.2。
4. **写成片段（脚本）**：转换结果按本轮输出格式、每个提案一个文件写成 `modeling/parts/00-ossie-*.json`（§9），和智能体自己写的片段一起合并，最后只提交一次，生成一批提案。
5. **快照列由智能体先判断**：纯 Ossie 没有快照信息，结构上也无法断定（§4.3）。表结构在工作包的表清单里一开始就有，智能体在运行脚本前参考材料描述和表结构，按**登记表**判断快照列（如 `sales.customer_df=ds`），写进 notes 并说明依据。不确定的表不传，按非快照处理。
6. **一次转换内设快照列并证明物理连接**：脚本把 `--snapshot 表=列` 一并交给平台。数据集按表名匹配到某张登记表时，采用该表的快照列（列必须在登记列中，否则报错不设）。物理连接的目标端：登记表主键去掉快照列后与连接的目标列组相同，就证明同一天里目标唯一，转换为关系对接。内网材料 14 条中预计 5 条可以证明；其余 9 条目标列只是主键的一部分（如组件表主键是“组件名、环境、区域、日期”，连接只用“环境、组件名”），仍报待补全，交给智能体和用户判断。智能体之后若改了快照判断，可以再运行一次脚本，结果按 §9 写入，被改过的文件不会被悄悄覆盖。
7. **登记表主键不当作对象的来源键。** 许多对象是从别的表去重得到的（例：“环境”对象从组件表的 `env_name` 列映射），对象的来源键仍取它的标识列。登记主键只用于第 6 步证明连接唯一。
8. **人确认**：快照列、证明出的连接、智能体补全的内容都在提案里，用户审阅接受；提案说明写明“快照列由智能体判断，依据……”。

## 4. 用户决定（2026-11-24）

### 4.1 入口：脚本调用平台（C）

由智能体在对话中运行脚本，脚本用本轮运行凭据调用平台导入。不在运行开始前由平台自动导入（A），也不让用户改用“导入文件”（B）。

理由：沿用用户最初的想法“对话里识别到是 Ossie 后用脚本处理导入”。技能运行在 DataAgent 沙箱里，拿不到平台导入器，但已有按运行凭据调用平台的先例（`prepare_result.py` 提交检查），不用新开 MCP 工具。结果作为片段并入本轮输出，只有一个会话、一批提案。

### 4.2 按表名找不到或找到多张表时

例：数据集 `orders` 的 `source` 是 `sales.order_df`。

| 情况 | 处理 |
|---|---|
| 本会话关联的表中恰好一张 `sales.order_df` | 采用其连接 |
| 本会话没有关联，但工作空间其他连接里恰好一张 | 只报告，不自动采用；智能体请用户把这张表加到本会话 |
| 多个连接都有 `sales.order_df` | 报告歧义，请用户选择 |
| 都没有 | 报告缺表 |

### 4.3 快照列：确定性做不了，交给模型判断、人确认

纯 Ossie 没有快照信息。快照列是数据集上的设置（`snapshot_date_column`）：表每天存一份全量，这一列是日期，查询时只取某一天。内网材料对应的表大多在主键里带 `ds`，但主键去掉对象标识后通常不止 `ds` 一列（例如组件表剩 `ds, env_name, zone`），从结构上无法断定哪一列是快照日期，所以平台不自动设置。由智能体在运行脚本前按登记表判断并写明依据，用户在审阅提案时确认。这和普通建模一致：从表建模时，快照列本来就由智能体在 `entities.json` 的 `snapshot_date_column` 里判断（PR #105）。

## 5. 例子（虚构）

材料：`order` 映射自 `sales.order_df`（列 `order_no, customer_no, ds`，登记主键 `order_no, ds`），`customer` 映射自 `sales.customer_df`（登记主键 `customer_no, ds`），物理连接 `order_df.customer_no → customer_df.customer_no`。

| | 现在（对话） | 按本设计 |
|---|---|---|
| 读材料 | 智能体逐段读、手写片段 | 导入器一次转换 |
| 数据集连接 | 智能体对着表清单逐个填 | 按 `sales.order_df` 在本会话关联表中唯一匹配 |
| 快照列 | 智能体判断 | 运行脚本前，智能体按表清单判断 `ds` 是快照列并写明依据，用户审阅时确认 |
| 订单 → 客户连接 | 待补全 | 同一次转换中：`customer_df` 主键 `(customer_no, ds)` 去掉 `ds` 为 `customer_no`，与连接目标列相同，已证明 |
| 智能体剩余工作 | 全部 | 报告中的待补全项 |

## 6. 影响范围

- 平台：新增按运行凭据访问的转换接口（只返回，不落库）；导入器按表名接连接、按传入的快照列证明物理连接。“导入文件”路径也能用按表名接连接。
- 技能：新增 `import_ossie.py`（调用接口，写片段和报告）；`extract.md` 或 `reading-ossie.md` 写明“遇到 Ossie 先运行脚本”；`import-completion.md` 改为处理本轮转换报告。字节预算按 `offline_budget.py` 核算。
- 本体标识与表主键不一致的报告（`docs/TODO.md` 第 7 项）一并实施：第 6、7 步要读登记主键，顺带列出差异。

## 7. 实施前核实

- 转换结果能否完整写成本轮输出格式的片段：数据集、映射、指标、规则、成员条件、关系对接。不能表达的部分要列出来，按报告交给智能体。
- 片段里的元素和智能体后写的片段同名时怎么合并，比如智能体为同一对象补描述。
- 运行凭据接口的权限和大小上限：一万行材料大约 400 KB。

## 8. 评审修订（Codex，2026-11-24）

评审记录在 `~/.agents/handoffs/2026-11-24-codex-ossie-in-conversation-review/`，8 条全部核实成立。结论：入口和单批提交可以保留，现有输出格式能承载导入结果（平台对照本轮固定草稿生成提案 `items`，新元素用稳定 `client_ref` 互相引用）。修订如下：

| # | 问题 | 处理 |
|---|---|---|
| 1 | 提交时每个改动的数据集都必须绑定本轮范围内的连接，否则整批拒绝（`services/table_submission.py` `TABLE_NOT_IN_SESSION_SCOPE`） | 平台转换时按本轮表范围预检：缺表、歧义、表不在本会话的数据集不进片段，连同依赖它们的映射、关系对接、指标一起列入报告，其余照常输出；智能体请用户补表后开新一轮 |
| 2 | 片段只拼接，没有覆盖语义：同一 `client_ref` 重复会报错，另起引用再建同名对象会触发重名校验；`expand_tables.py` 还会再生成一遍对象、数据集和映射 | 见 §9 待定 |
| 3 | “主键去掉快照列等于目标列”只说明目标在一天内唯一，生成的 `DirectJoin` 仍须对接唯一属性或完整标识，一对一还要求源端唯一；`MappingTableJoin` 列序接反也可能通过 | 登记键证明只作为输入交给关系转换，不写入数据集键、不恢复属性唯一性；生成前逐项核对两端绑定、键序、基数，核心校验不通过就报告，不输出 |
| 4 | 材料上传只存 UTF-8 文本，Ossie 交换 ZIP 进不来 | 本期只支持单个 Ossie JSON 材料；ZIP 仍走“导入文件” |
| 5 | 快照数据集按各自最后有数据的日期取行（`docs/concepts/time-and-snapshots.md`），订单最新为 24 日、客户最新为 25 日时，关联到的是客户次日的状态 | 这是现有快照语义，不由本设计改变；证明只说明“至多一行”。`--snapshot` 用本轮表引用 `t#` 指定表，避免不同连接下同名表混淆；快照列须是登记列，类型为日期、日期时间、字符串或整数 |
| 6 | 复用运行凭据时，提交端允许已结束的运行取回结果，MCP 只查读权限 | 转换接口单独校验：签名凭据、空间与会话匹配、运行仍在进行、用户仍有编辑权限。请求只传材料 ID、哈希和快照选项，平台自己读原件，不回传 400 KB 原文 |
| 7 | 报告的行号来自格式化后的文本，直接引用会被证据校验拒绝；notes 里的快照依据不会进提案 | 证据定位到已登记材料的原始行（沿用格式化材料机制）；快照判断的依据写进对应数据集提案的 `reason`，表结构证据引用 `t#` |
| 8 | 单批最多 500 条提案 | 报告先给出条数和剩余容量；超限时按依赖分组，由智能体在提交前请用户确定本批范围。内网材料估计约 350 条 |

## 9. 智能体润色导入的内容（用户 2026-11-24 决定）

流程是“导入完，顺手润色，再通过检查”。不加补丁格式，不把导入内容设为只读：

1. **按元素拆成小文件。** 脚本把转换结果直接写在 `modeling/parts/` 下，每个提案一个文件，例如 `00-ossie-object-customer.json`、`00-ossie-dataset-customer_df.json`、`00-ossie-mapping-customer.json`（合并脚本只读这一层的 `*.json`，按文件名排序，不进子目录）。每个文件都是普通片段（一个 items 数组），智能体给“客户”补描述只改 `00-ossie-object-customer.json`，和平时编辑片段一样。
2. **重跑不悄悄覆盖。** 脚本在 `modeling/tmp/ossie-manifest.json` 记下每个文件生成时的哈希。再次运行时，若有文件被改过，就不写入，列出改过的文件并退出；智能体确认放弃修改时加 `--force` 重新生成。被删除的文件同样算改动，避免删掉的元素被重新生成。
3. **合并和检查照旧。** 这些文件与智能体自己写的片段一起由 `prepare_result.py` 合并，走现有本地预检和平台检查。引用用稳定的 `client_ref`，改名不影响引用。
4. **表展开不重复生成。** `expand_tables.py` 跳过导入已覆盖的对象，不再生成同名的对象、数据集和映射。
5. 平台的提交入口不变，一轮一批提案。
