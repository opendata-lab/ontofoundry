# 建模失败后续做修正（按基线保留成果）

日期：2026-11-13。状态：已确认方向，待实施。来源：大型建模会话中，运行结束时提交未通过平台检查、修正轮次用完，用户重新发送后 Agent 从头建模，耗时长、成本高且没有意义（2026-11-13 用户反馈）。分析见 `~/.agents/handoffs/2026-11-13-codex-modeling-cost/`（只读源码核对，节省比例为估算）。

实施见[计划](../plans/2026-11-13-modeling-resume-plan.md)。

## 1. 现状

- 每条建模消息生成新的运行令牌（run token）；DataAgent 话题（topic）跨轮复用，工作区文件保留。
- `integrations/dataagent/shared/scripts/init_workflow.py` 发现片段属于另一个运行令牌时，把 `modeling/parts/`、`modeling/checks/` 移入归档，本轮从空目录开始；`plan`、`notes` 不处理，可能与新片段不一致。
- 收尾时平台检查不通过最多修正三轮（按运行令牌计）；仍不通过就不提交，会话标为 `failed_permanent`（`services/model_result.py`）。
- 因此修正轮次用完后，用户再发消息，Agent 重新计划、读材料、抽取全部片段，只为修几处检查错误。
- 修正轮次用完后，平台提示“删去仍不通过的提案组后提交”，但代码在看内容之前就按轮次拒绝，这条路走不通（`services/proposal_submit.py`）。

## 2. 决定

| 编号 | 决定 | 状态 |
|---|---|---|
| MR-01 | **成果按基线保留，不按运行令牌**：已有片段能否沿用，取决于它所依据的内容有没有变，而不是哪一轮写的。基线包括：发布版本 ID 和摘要、会话草稿摘要、材料清单摘要、表范围与结构摘要、实例基线（变化序号、修订号、摘要）。会话修订号每条消息都会增加，不作为判断依据。来源：用户提出以版本为基线；Codex 核对补全了草稿、材料、表和实例。属于执行优化，不进入本体模型。 | 2026-11-13 用户确认方向 |
| MR-02 | **首版只做保守续做**：同一会话、基线完全不变、平台确认上一轮没有入库任何批次时，新运行保留上一轮的片段、检查报告、计划和笔记，直接进入收尾：读上次的检查报告，只改报错的片段，合并后重新提交。新运行使用自己的凭据和三轮修正预算。其他情况（基线变化、上一轮已入库、片段缺失）沿用现在的做法，整体归档后从头开始。 | 2026-11-13 用户确认范围 |
| MR-03 | **是否续做由平台判断**：平台按上一轮运行令牌查询是否有入库批次，不依赖 Agent 本地的成功记录（响应可能丢失）。上一轮已入库时，即使基线没变也不续做，避免重复提案。 | 2026-11-13 用户确认范围 |
| MR-04 | **修正提示改正**：轮次用完时提示改为“本轮修正已用完，结果未提交。请在回答中说明未通过的问题；用户再次发送消息时，可在本轮成果上继续修正”。 | 2026-11-13 用户确认范围 |

不做：跨会话共享成果、按输入差异只重做受影响部分、部分提案入库（与[串行原子建模](2026-10-26-serial-atomic-modeling.md)冲突）、DataAgent 上下文裁剪和换用便宜模型。这些等有了分阶段用量数据再定。

## 3. 怎样触发续做

用户在失败的结果后再发一条消息。是否续做只看第 2 节的条件，不看消息内容：

| 例子 | 基线 | 结果 |
|---|---|---|
| 修正轮次用完、未提交，用户发“继续”（少于 20 字，不成为材料） | 不变 | 续做：保留片段，只修报错 |
| 同上，但用户发了一段 20 字以上的新要求（成为新材料） | 材料变了 | 从头开始 |
| 上一轮已入库，提案被全部拒绝后再发消息 | 不变 | 从头开始（不续做已提交过的片段） |
| 期间接受了别的提案、换了数据表或发布了新版本 | 变了 | 从头开始 |

构建页在失败结果下方提示：“发送‘继续’可在本轮成果上修正后重新提交；发送新的要求会重新建模。”

## 4. 机制

1. **平台**（`services/modeling_input.py`、`api/agent_conversation.py`）：每次运行计算基线摘要，存入运行清单 `run_manifest_json.baseline`。新消息替换清单前，取上一轮清单比较：上一轮是建模模式、结果为 `failed_permanent`、按其运行令牌查不到入库批次、基线完全相同，则在工作包 `run` 中写入 `resume: {"previous_run_token": "...", "reason": "repair"}`；否则不写。
2. **初始化**（`init_workflow.py`）：工作包带 `resume` 且工作区标记的运行令牌等于 `previous_run_token`、`modeling/parts/` 中有片段时，保留 `parts`、`checks`、`plan`、`notes`，改写标记为本轮令牌，打印续做提示（上次检查报告的位置、直接读收尾步骤）；否则把四者一起归档（现在只归档 `parts` 和 `checks`）。片段缺失或无法读取时如实提示，并按从头开始处理。
3. **技能路由**（`skills/ontology-discovery/SKILL.md`、`shared/references/steps/finish.md`）：增加续做入口：初始化提示续做时，跳过计划和抽取，读收尾步骤，按上次检查报告修改片段，再合并提交。计划模式下仍需提交一份简短计划（“修正以下检查错误后重新提交”）获批后再改，不沿用上一轮的批准。
4. **提交**：沿用本轮凭据、目标状态和批次归属；修正轮次按本轮计。提交成功后把片段移出活动目录（保留留档）。

## 5. 验收

| 场景 | 预期 |
|---|---|
| 修正轮次用完未提交，基线不变，用户发“继续” | 新运行保留片段，不重新读材料和抽取，直接修正提交；有新的三轮修正 |
| 草稿、材料、数据表或实例基线任一变化 | 不续做，四类工作文件归档后从头开始 |
| 上一轮已入库（含响应丢失的情况） | 不续做，不重复提交 |
| 上一轮片段在工作区中缺失 | 如实提示后从头开始 |
| 计划模式下续做 | 先提交修正计划，获批后才改片段 |
| 修正轮次用完的提示 | 不再建议“删去提案组后提交” |
