# 提案检查前移到对话、入库不整批拒收

日期：2026-10-23。状态：CK-02、CK-04 有效；CK-01 中“平台不可达时说明未做检查”与 CK-03 已被 `2026-10-26-checks-before-output.md` 取代（检查失败不放行，删除修复任务与平台消息）。

## 1. 背景

内网一次建模：Agent 合并结果时技能检查通过（105 条、0 错误），在对话中说“已发布”；平台入库时再做整图校验，发现一条关系的目标连接列不是唯一属性或完整标识（`domain/validation.py`），退回修正一轮后次数用完，整批 105 条被拒收。拒收原因显示在右侧提案面板角落，对话里却是“已发布”，用户无处重试。

同一批数据还暴露另一问题：导入或生成的子对象共用父对象的表，但没有自己的映射记录，读实例时报“子对象成员绑定待补全”，界面上无处补。

## 2. 已确认决定

| 编号 | 决定 | 状态 |
|---|---|---|
| CK-01 | 规则只有一份，在平台。技能合并脚本本地检查通过后，把结果交平台用同一套规则检查，有问题当场在对话中修正后再交；平台不可达时说明未做平台检查，不冒充通过。技能不复制平台规则。 | 已确认 |
| CK-02 | 入库不再因整图规则拒收整批。按依赖顺序逐组应用提案，使候选图不合法的组标为“不可接受”并写明原因，其余正常待审。格式、引用、固定上下文不符等契约错误仍不能入库。 | 已确认 |
| CK-03 | 失败原因在 Agent 运行中通过工具报错看到：合并脚本调用平台检查（CK-01），平台的契约错误与不可接受原因作为脚本输出返回，Agent 当场修正。运行结束后仍失败（如没写结果、修正次数用完）或有不可接受的提案时，对话里说明原因并放一个“重试”按钮；按钮只在输入框填入“重试”并自动发送。右侧提案面板不再显示运行报错。 | 已确认（用户 2026-10-23） |
| CK-04 | 子对象共用父对象的表时，不要求它有自己的映射记录：祖先已绑表即按共用父表读取，只要求成员条件（父表中哪些行属于本对象）。根因在平台：成员条件已写时仍要求映射记录。技能侧不另加检查（用户 2026-10-23）。撤回“填成员条件时界面自动创建映射”的改动，报错改为指明在概览中补成员条件。 | 已确认 |

来源：CK-01～03 是运行协议与界面，不进入本体模型；CK-04 依据“能从已有定义推导出的不存进模型”，删除一条可推导的必需记录，不新增概念。

## 3. 平台检查接口（CK-01）

- `POST /api/v1/ontology/workspaces/{workspace_id}/runs/{run_token}/proposal-check`，凭据为该轮运行级授权（与 MCP 同一授权），请求体为结果文件内容，只检查不入库。
- 返回与入库相同的诊断：契约错误（拒收）与不可接受的提案组（附 client_ref、原因），文案按 2026-10-23 报错格式。
- `prepare_result.py` 本地检查通过后自动调用；输出“平台检查通过”或逐条问题与下一步；平台不可达时输出“提示 [PLATFORM_CHECK_SKIPPED]”及原因。

## 4. 入库（CK-02）

- `parse_result` 保留契约检查；`group_items` 的整图校验改为逐组应用：按依赖拓扑序，某组应用后候选图不合法则跳过该组并记录原因，依赖它的组一并标为不可接受。
- 不可接受的提案以“不可接受”状态和原因展示，不能接受；其余照常。批次在对话中报告“N 条可审，M 条不可接受”。

## 5. 对话中的失败与重试（CK-03）

- 运行结束为失败，或批次中有不可接受的提案时，对话中追加一条平台消息：原因摘要、受影响的提案数，一个“重试”按钮。
- “重试”按钮只在输入框填入“重试”并以建模模式自动发送，不带其他参数。失败原因在运行中已经由合并脚本的平台检查作为工具输出交给 Agent，不再另外附进提示。
- 右侧提案面板去掉运行失败的提示块。

## 6. 子对象共用父表（CK-04）

- `domain/bindings.py`、`services/instance_plan.py`：子对象无自身映射而祖先有映射时，按共用父表处理；无成员条件时报“还没有成员条件：在概览中编辑成员条件，写明父表里哪些行属于本对象”。
- 前端 `bindingMode` 与之一致（已是如此）；撤回 `ElementPanels.tsx` 中自动创建映射的改动。
- 导入：源中有子类型条件则转换，没有则列入导入待补项。

## 7. 实施顺序

1. CK-04（平台推导、报错、技能提示、撤回界面改动）。
2. CK-02 入库逐组校验与不可接受状态。
3. CK-03 对话中的失败消息与重试。
4. CK-01 平台检查接口与合并脚本调用。

每步离线测试通过后提交；全部完成后用一个带继承和关系的虚构场景跑一次真实运行验证（需用户确认预算）。
