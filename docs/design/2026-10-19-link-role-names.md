# 恢复二元关系两端角色名称

状态：已确认，2026-10-19。本文对核心模型设计 §3.4、RT-21 及关系弹窗布局中不保存独立角色名的决定作定向修订。

## 已确认决定

| 决定 | 内容 |
|---|---|
| 字段来源 | Apache Ossie 的 roles[].name；页面组织参考 Foundry 每侧的 display name |
| 语义性质 | 业务语义：同一对象类型在不同关系位置扮演的角色，不是执行优化或权限角色 |
| 新增字段 | LinkType.source_role_name、target_role_name，可选字符串或 null，沿用显示名称的长度及规范化规则 |
| 方向 | 字段属于参与端：来源端是下属，目标端是主管；从来源遍历显示目标角色“主管”，反向遍历显示来源角色“下属” |
| 既有字段 | name 仍是关系名称/正向读法，inverse_name 仍是反向读法，technical_name 仍是既有引用；不互换、不删除 |
| 为什么不能复用 | “汇报给/管理”不能稳定推导“主管/下属”；两个读法与两个角色是不同信息 |
| 空值及旧数据 | 不猜测、不回填历史名称；角色名缺失时方向标题使用既有正反读法，再回退到对象名 |
| 数据保存 | 沿用版本、草稿及提案 JSON，不改变数据库表结构，不新增 Alembic 迁移 |
| 哈希兼容 | 未配置的角色名在语义规范化中省略，避免旧快照仅因新增 null 默认值发生哈希漂移；非空角色名正常参与哈希及冲突检查 |
| 验证安排 | 按用户要求不运行测试、构建、lint 或自动化视觉测试；模型生成契约及类型属于必要产物生成 |

## 界面

关系概览继续使用概览 / 映射 / 规则页签，实例在概览下方。来源对象/目标对象同行，下面填写来源端角色名/目标端角色名；正向说明“每个员工有一个主管”，反向说明“每个员工有多个下属”。未填写角色名时继续显示对象类型，不制造“主管”等默认值。顶部关系名称与技术名保留，反向读法输入仍暂时隐藏且保留数据。关联实例表头、实例详情、对象关系列表及派生关系选择优先展示遍历目标角色，图上连接动词保留既有 name。自关联在对象关系列表中按两个方向展示，避免只看到主管或只看到下属；绑定及规则仍归属于同一 LinkType。

## Ossie 交换

- 二元实体关系：导入 roles[0].name 为 target_role_name，不再报告该目标角色丢弃。首角色隐式，不伪造源角色名。
- 导出目标角色名写入原生 roles[0].name，并在 verbalizes 中使用匹配的 {concept:role} 占位符。没有目标角色名的自关联继续生成 related；通过扩展记录是否为生成占位符，避免回读时将其当作用户业务角色。
- 原生目标角色名若与源概念名冲突或含占位符分隔字符，导出时为变量生成无歧义别名，真实显示名由扩展保存；变量名用于交换，不替换核心显示名。
- 源端角色名及精确角色空值通过 ai_context.ontofoundry.link_role_names 保存，路径与现有显示扩展一致。仅保存已有两字段以保证往返，不增加核心概念。
- 多元关系重化为中间对象时，将实体端角色名保存到生成关系的 target_role_name；值角色暂仍按 RT-21 报告不独立保存。关系重化本身继续遵循 RT-27。
- 不扩大规则表达式语言；原生角色变量继续由现有变量绑定转换器处理。

## 例子

虚构工作空间“云杉业务”：员工小林汇报给员工小周。来源端角色名“下属”、目标端角色名“主管”，name=汇报给，inverse_name=管理，multiplicity=many_to_one。同一关系从小林看是主管小周，从小周看是下属小林。角色名本身不产生新的对象类型或实例事实。

同步技能核心模型参考，提示词无需改变；发布源码到已配置的 SKILLS_ROOT_DIR 并按现有运行方式重启。若本机没有可识别的 DataAgent 配置，不猜测部署路径，保留源码并明确报告未部署。

## 名称与 Ossie 原生字段的边界

Ossie relationship.name 是关系标识的一部分，对应当前 technical_name；roles[].name 是额外角色名；verbalizes 保存一个或多个自然语言读法。Ossie 没有 inverse_name 字段。当前 name/inverse_name 是此前核心模型从读法提取的简化表达，不宣称与 Ossie 原生字段同名同义。本轮恢复角色名不擅自删除这两字段；用户后续讨论是否恢复完整读法时需另行确认模型变更。
