# 演示手册：咖啡渠道销售（约 20 分钟）

主线：**本体是一层业务语义，向上连着非结构化的文档，向下连着结构化的数据表。**
今天用同一个业务空间演示两种建模方式，再把这层语义通过 MCP 交给智能体问数：

| 方式 | 输入 | 产出 | 验证的关系 |
| --- | --- | --- | --- |
| 自上而下 | 业务文档 + 目标范围 | 对象、属性、关系、规则，以及**文档中的业务实例**（带原文证据） | 本体 ↔ 非结构化数据 |
| 自下而上 | 选定的数据表 | 对象/属性补全、**数据映射**、**关系的字段连接** | 本体 ↔ 结构化数据 |

> 浏览器两个标签：A = OntoFoundry `http://127.0.0.1:8000`，B = DataAgent `http://localhost:3001`。
> 缩放 110%～125%。「旁白」是建议说法，「备用」是现场出状况的退路。

---

## 演示前 30 分钟检查

- [ ] 服务都在：PG（`docker start of-local-pg`）、DataAgent 后端 8900、DataAgent 前端 3001、
      OntoFoundry `make serve`（8000）。命令见 [README](README.md#环境与地址)。
- [ ] 演示中**不要执行 `make build`**：会让已打开的页面加载旧文件失败。
- [ ] 防休眠：终端执行 `caffeinate -dimsu &`。Mac 休眠后 Podman 虚拟机时钟会落后，恢复时跳变，
      DataAgent 会把正在跑的建模任务当成超时（平台会自动跟随它的替换任务，但会多等一会儿）。
      **演示前与每次合盖/休眠后**执行 `docs/demo/coffee-channel-sales/scripts/sync_clocks.sh`，
      三个时钟（主机、MySQL、PG）相差不超过几秒。曾实测休眠后虚拟机时钟落后 1 小时 44 分，建模任务一直卡在“运行中”。
- [ ] 关掉占满 CPU 的进程（活动监视器按 CPU 排序；之前有一个 Safari 页面长期 100%）。
- [ ] A：咖啡渠道销售 → 空间设置 → 「DataAgent 连通性」四项「通过」。
- [ ] A：本体发布 → 版本历史只有 **v1**（自动建模结果）；本体视图的「数据映射层」为空。
- [ ] A：本体构建 → 会话下拉中有「渠道销售本体（演示预备）」「售后退货（备用）」「销售业务库映射（备用）」，
      两个备用会话的「提案」里是**待处理**提案。**不要提前接受。**
- [ ] B：选「咖啡渠道销售 · 问数助手」后，左侧历史里有「客户销售额排名」。
- [ ] 桌面放好 `materials/02-售后退货规则.md` 和 `materials/03-2026年1月退货登记.md`。
- [ ] 把下面两段「业务场景描述」复制到剪贴板工具里备用。

```text
目标范围：售后退货。复用已发布的客户和订单，补充退货相关的对象、属性、关系和规则，并把退货登记中的每一笔退货抽取为实例。
```

```text
目标范围：把销售业务库的四张表对接到已发布本体。复用已有的客户、订单、订单明细和商品，补全缺少的属性，为每个对象建立数据映射，并按关联字段为关系配置数据连接。
```

## 第 0 段 · 开场（1 分钟）

A 标签首页 → 点「咖啡渠道销售」。

旁白：「企业的知识一半在文档里，一半在数据库里，中间缺一层大家都认可的业务语义。本体就是这一层。
今天看这层语义怎么从文档里长出来、怎么接上数据库、怎么交给智能体用。」

## 第 1 段 · 自上而下：从文档建模（4 分钟）

1. 「本体构建」→ 会话下拉选「**渠道销售本体（演示预备）**」。
   - 左栏「选择已上传材料」：《渠道销售业务说明》；
   - 中栏：DataAgent 的建模过程（读材料 → 产出 → 自动校验 → 有问题自动修正）；
   - 右栏「提案」→ 点「**历史**」展开：业务对象、属性、关系、业务规则，点开一条看**原文证据**。
     （页面刚打开时右栏会空一两秒，等加载完再讲。）
   - 旁白：「模型只提『提案』，每条带原文证据，人接受了才算数。这一版已经发布为 v1。」
2. **现场再跑一次自上而下**（目标范围 + 文档 → 规则和实例）：
   - 会话下拉右侧「**+**」新建会话；
   - 「上传业务知识」依次上传 `02-售后退货规则.md`、`03-2026年1月退货登记.md`；
   - 「业务场景描述」粘贴第一段目标范围；
   - 点「**开始建模**」（不要在中间对话框回车，那是普通问答）。
   - 旁白：「它先通过 MCP 读已发布的本体，复用客户和订单；规则文档产出对象和规则，
     登记文档里的每一笔退货会被抽成**实例**。约 4 分钟，我们先做第二种方式。」

## 第 2 段 · 自下而上：从数据表建模（3 分钟）

1. 再点「**+**」新建一个会话。
2. 左栏「业务数据」→「**选择数据表…**」打开选表弹窗：数据连接为「销售业务库」→ 勾选 `customers`、`orders`、
   `order_items`、`products`（表多时可用搜索框过滤，再点「全选筛选结果」）→「**加入建模材料（4 张表）**」，弹窗自动关闭。
   - 左栏「选择已上传材料」里出现「数据表结构-销售业务库-…」，点开可看到系统读出的字段、主键、
     样例值和关联字段（例如 `orders.customer_id → customers.id`）。
3. 「业务场景描述」粘贴第二段目标范围 → 「**开始建模**」。
4. 旁白：「这次的输入不是文档，是数据库表结构。它会把表对到已有的业务对象上，补全属性，
   生成字段映射，并根据外键把『客户下单』这类关系落到字段连接上。」

> 两个现场建模并行进行，约 4 分钟。期间做第 3 段。

## 第 3 段 · 本体可视化（3 分钟）

1. 「本体视图」→「全局」：服务层、语义模型层（客户/订单/订单明细/商品）、实例与证据层、数据映射层。
   旁白：「现在只有语义层，上下两层都还空着——一会儿两条建模结果发布后，这两层会被填上。」
2. 「语义视图」：客户 →下单→ 订单 →包含→ 订单明细 →对应→ 商品。
3. 点「订单」→ 元素面板：「属性」「关系」「规则」（订单金额等于明细金额之和、仅已支付订单可发货）。

## 第 4 段 · 接受提案、人工把关、发布（4 分钟）

先发布自下而上，再发布自上而下。

**自下而上（数据表）**

1. 「本体构建」→ 会话下拉选第 2 段新建的会话（标题是那段目标范围的开头）。
   - **超过 6 分钟仍无结果，或出现失败/网络错误，立即改选「销售业务库映射（备用）」**，不要现场重试。
2. 右栏提案里依次指出（共 11 条）：**4 条编号类型修正**（客户/订单/商品/明细编号：文本 → 整数，依据是表字段 BIGINT）、
   **4 条数据映射**（客户 → customers 等）、**3 条关系字段连接**。
3. 人工把关示例：点开一条映射提案，看字段对应关系。旁白：「AI 提，人看；不对可以拒绝或改。」
4. 「**接受全部无冲突项**」→ 右上「**发布本体**」→ 发布页查看变更 → 点「**发布 v2**」→ 对话框里填发布说明
   `对接销售业务库` →「**确认发布**」。（提案面板刚打开时可能闪一下「暂无提案」，等列表出来再讲。）
5. 「本体视图」→「全局」：**数据映射层出现四张表**。点「订单」→「实例」（已对接数据的对象默认显示
   数据库实例）：真实订单逐页展示（实例页不显示总数，总量留给问数环节回答 780 张）。
   旁白：「本体不搬数据，按映射实时查询。」

**人工修正（1 分钟）**

5a. 「本体对象」→「订单」→「实例」：订单状态在库里是 `paid` / `shipped` 这样的代码。
    旁白：「AI 已经按表结构把类型对齐了，但代码含义这种业务知识，还是人最清楚。」
5b. 「属性」→「编辑」→「订单状态」的说明改为 `取值：paid=已支付，shipped=已发货` →「保存」。
    保存即生成新版本，下游（包括智能体）马上读到。
5c. 若「实例」页出现类型提示（例如「客户编号：本体定义为文本，数据中为整数」），就按提示在「属性」里改类型，
    同样是一次人工修正。

**自上而下（文档 + 范围）**

6. 会话下拉选第 1 段新建的会话；**超过 6 分钟或失败就改选「售后退货（备用）」**。
   页面上的运行状态长时间不变时，刷新一下页面再看。
7. 提案里指出：新对象「退货单」、它和订单、客户的关系、3 条规则，以及 **3 条退货实例**
   （RT-202601-001～003），点开实例看属性值和原文证据。
   - 若实例上缺客户编号之类的值：「文档里本来就没有系统编号。平台不让模型编，标记为『待补全』，
     不影响发布；之后可由数据侧补齐或人工补。」
8. 接受全部 →「发布本体」→「**发布 v4**」（版本号以页面为准）→ 发布说明 `新增售后退货` →「确认发布」。发布页的「警告」里会列出待补全项和尚无属性的对象。
   旁白：「文档只提到概念、没写字段的对象，会提示『可从数据表补全或人工添加』——
   这正是自下而上要补的部分：**文档给语义，数据表给结构**。」
9. 「本体视图」→「全局」：**实例与证据层出现 3 条退货实例**。
   旁白：「这就是本体和文档的关系：概念从文档里来，文档里的事实也挂在同一套概念下，可追溯到原文。」

> 两个备用会话与现场会话内容相同，**同一方向只发布一个**，否则第二个会因重复而冲突。

## 第 5 段 · MCP 对外服务（2 分钟）

1. 「本体发布」→「**服务接入**」。旁白：「发布的本体同时提供 REST 和 MCP，11 个只读工具：
   8 个查本体，3 个查业务数据（数据库实例和文档实例）。」
2. 「只读访问令牌」：名称 `领导演示问数`，勾选「**允许查询业务数据（问数需要）**」→「创建令牌」。
3. 「**复制 MCP 配置**」。旁白：「令牌只读、按空间隔离；数据库用只读账号。」

## 第 6 段 · DataAgent 新建智能体并问数（4 分钟）

1. B 标签 → 设置 →「MCP 服务」→「导入」→ 粘贴 → 确认，`ontofoundry` 显示 11 个工具。
2. 「智能体」→「新建智能体」：名称 `渠道销售问数`；自定义提示词粘贴
   [`agent_ontofoundry_qa.md`](../../../integrations/dataagent/agents/agent_ontofoundry_qa.md) 的「系统提示词」；
   工具勾选 `ontofoundry`。
3. 右侧「预览与调试」：`星海贸易在哪个城市？什么时候签约的？` → 上海，2025-10-02（约 15 秒）。
4. 「发布」→ 勾选确认 →「确认发布智能体」。
5. 对话页选该智能体，依次问：
   - `一共有多少张订单？订单总金额是多少？` → **780 张，269,516 元**——**结构化数据**。
     要翻完 8 页再精确求和，约 1～2 分钟：**先发出这个问题，再讲解**，回头看结果；
   - `1 月有哪些退货？退款合计多少？` → **3 单，合计 376 元**，带原文出处——**非结构化数据**。
6. 打开已有对话「**客户销售额排名**」：远山咖啡 38,348 元居首。
   旁白：「同一个智能体，同一套业务语言，既能问数据库，也能问文档里的事实。」

> 备用：新建智能体出状况，直接选「**咖啡渠道销售 · 问数助手**」提问。

## 收尾（30 秒）

「文档自上而下长出语义，数据表自下而上接上语义，人确认后发布成版本，通过 MCP 交给任何智能体。
语义只维护一份，模型和智能体可以换。」

## 现场别做的事

- 不在构建页中间对话框回车建模；建模只点「开始建模」。
- 不现场问大范围汇总的新问题（各城市销售额等）——能答对但要 2～3 分钟，用「客户销售额排名」代替。
- 同一方向的现场会话和备用会话只发布一个。
- 演示期间不重新构建前端。

## 领导可能问的问题

| 问题 | 回答要点 |
| --- | --- |
| 模型建错了怎么办？ | 只出提案；每条有证据；人可拒绝或修改；发布前有校验和差异对比 |
| 文档和数据库说法不一致怎么办？ | 两边都对到同一个业务对象上；冲突在提案和发布合并时逐项呈现，由人决定 |
| 问数会不会编数？ | 只能经 MCP 取数；统计翻完全部分页；答案带口径和来源 |
| 数据安全？ | 令牌只读、按空间隔离、查数据需额外授权、数据库只读账号；版本里不存密码 |
| 换模型 / 换智能体平台？ | MCP 是标准协议，本体不绑定模型 |
| 数据量大了？ | 目前按映射实时分页，适合明细和中小规模统计；服务端聚合是下一步 |
| Action 能执行吗？ | 目前是建模层定义，执行引擎在规划中 |
