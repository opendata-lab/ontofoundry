# 证据与实例

[概念概览](README.md) · [主设计文档 §3.1、§3.2、§4.6、§13.4、§14.2](../design/2026-10-14-core-model-and-format-adapters.md)

本文说明 core-1 的目标模型与行为，状态为设计定稿、待实施。JSON 示例中的业务和数据来源均为虚构；片段不是完整导入包，完整包形式见[格式与转换](formats.md)。字段表逐项说明何时填写、空值与默认行为。

## 1. 概述

退货登记写着“R-1 退款 50 元”，可以保存为一条退货单对象事实，再用证据指向支持它的原文。文档实例保存具体业务事实；证据说明某个定义或事实依据什么成立。

需要从材料或人工确认中保存可追溯事实时使用它们。材料证据包含材料身份、哈希、位置和引文，人工证据包含确认说明、作者与时间。不要用文档事实缓存业务库全表，也不要把材料当作物理数据集；MCP 的实例工具只读取文档事实，数据库统计由 agent 的查询工具完成。

## 2. 字段

| 字段 | 类型 | 填写要求 | 说明 |
|---|---|---|---|
| `MaterialObject.id` | UUID | 必须提供。 | 此字段保存文档对象事实身份，不用业务编号拼接生成。 |
| `MaterialObject.type_id` | UUID | 必须提供。 | 此字段引用对象事实的具体对象类型。 |
| `MaterialLink.id` | UUID | 必须提供。 | 此字段保存链接事实的稳定身份。 |
| `MaterialLink.type_id` | UUID | 必须提供。 | 此字段引用链接事实使用的二元关系类型。 |
| 对象 `values` | 技术名到标量值的映射 | 可省略，默认空映射。 | 此映射保存本类型有效属性的标量值，允许事实信息尚未完整。 |
| 链接 `source_id` | UUID | 必须提供。 | 此字段引用源端文档对象事实。 |
| 链接 `target_id` | UUID | 必须提供。 | 此字段引用目标端文档对象事实。 |
| 事实或定义 `evidence` | Evidence 数组 | 可省略，默认空数组。 | 此数组保存支持该事实或定义的材料或人工依据。 |
| 证据 `id` | UUID | 必须提供。 | 这是该条证据的稳定身份。 |
| 证据 `kind` | 枚举 | 必须提供。 | material 表示材料证据，manual 表示人工确认。 |
| 材料 `material_id` | 字符串 | 材料证据必须提供。 | 此字段引用作为依据的材料。 |
| 材料 `material_sha256` | 字符串 | 新材料证据必须提供。 | 此字段保存原材料内容的 SHA-256，用于定位内容和校验完整性。 |
| 材料 `locator` | 对象 | 材料证据必须填写。 | 此对象保存原文位置，行号从 1 开始，标题可以为空。 |
| 材料 `quote` | 字符串 | 可以省略。 | 此字段保存支持该条定义或事实的原文引文。 |
| 人工 `note` | 字符串 | 人工证据必须提供。 | 此字段说明人工确认了什么以及确认理由。 |
| 人工 `created_by` | 字符串 | 人工证据由服务端填写。 | 此字段记录确认者身份，跨环境搬迁时保留原作者。 |
| 人工 `created_at` | 时间字符串 | 人工证据由服务端填写。 | 此字段记录人工确认的时间。 |


## 3. 例子

以下是客户A、退货单和二者关联的完整事实片段，类型与属性定义沿用[文档事实样例](../design/core-1-examples/07-instances-and-evidence.json)。材料 id 与哈希仅示意字段形状，实际导入须有对应内容，不能把该示意哈希当成已校验材料。

        "is_vip": true

            "heading": null,

界面打开退货事实可显示单号 RT-0103、退款 168、登记日期及材料证据；直接邻接列出客户A，查看邻居时另行读取。若退货金额尚未确认，values 可以缺 refund，平台保存事实并提示补全，不编造零值。

数据库“全部退货总额”应由 agent 查授权数据库聚合，不能把 search_objects 翻页得到的少量文档事实当作数据库全集。

文档事实读取时依次用有效标题属性值、完整业务标识元组、可见非空材料 quote 的前 80 个字符、事实 UUID 推导 display_text。null 和空字符串无显示值，0 和 false 有值；标识按属性 UUID 顺序，缺任一项就跳过整组；多个 quote 按证据 UUID 顺序取首项，截断只影响显示。只有人工 note 或无可见引文时继续回退 UUID。UI 与 MCP 的 display_text 只读，不写入核心；搜索覆盖推导显示文本和属性值。数据库实例仍按标题、完整标识、物理键回退。

文档事实、链接与证据导入只按 UUID 匹配，没有自然键，不因相同编号或引文合并；证据匹配不改变其归属。

AI 从不同文档抽出同一业务标识的事实时，各自形成新建提案。审阅时，已有同对象类型、同完整业务标识的事实只触发重复提示，不阻断或自动合并。用户可以两条都接受、只接受一条，或将新建改为对已有事实的更新提案并追加证据；更新保留已有 UUID。缺完整标识时不猜重复。是否合并由人决定，导入的 UUID 匹配规则不变。

例如两份材料各抽出 customer_no=C001 的客户事实 F1、F2，电话分别为111、222，证据分别为 E1、E2。若两条都接受，查询返回两个 UUID，get_object 分别读取各自的值、证据和邻接；若改为更新 F1，则以审阅确认的更新内容和追加证据保存到 F1，不自动把冲突值混在一起。

## 4. 建模建议

| 材料 | 行号 | 原文 |
|---|---|---|
| 退货登记 | 2 | R-1 退款 50 元 |
| 退货登记 | 3 | R-2 金额待确认 |

正例：保存 R-1 金额为 50，并引用第 2 行；R-2 保持金额未完整。

反例：从上一行复制 50 到 R-2 会得到无依据的值；把整篇材料挂上也不能证明这笔金额。

正例：一段材料明确写出单号和退款金额，在退货事实及关联事实上各保存相应引文。反例：把整篇材料挂到所有元素，却没有可定位的原文与行号。

不要把文档材料直接视为已绑定数据集。材料支持解释与证据，Dataset 登记物理表，两者用途不同。人工确认可用 manual 证据，不能捏造材料行号。

跨环境搬迁需要材料证据时导出完整原生包。单文件只带模型，目标环境找不到相同哈希的材料时会丢该证据并报告。虚拟父对象的事实保存在具体子类型上，不能直接在虚拟父上创建一条无具体类型的事实。

## 5. 校验与限制

链接端点必须存在且类型兼容关系定义，继承允许兼容子类型端点。文档事实可缺少 required 或 identifier 声明的值而保留并提示补全；事实 UUID 不意味着业务标识已完整。

材料行号须有序，结束不早于开始；哈希标识内容版本，内容变化不能沿用旧哈希伪装相同证据。原生完整包按 SHA-256 复用或重建材料并重写 material_id，原文、行号和内容哈希保持。

search_objects 与 get_object 只读已接受且获授权的文档事实，按事实 UUID 寻址并返回。get_object 的直接邻接属于该 UUID，按关系和方向分页，不递归展开全文；没有 can_read_instances 权限不得读取事实或证据。父查询保留实际 type_id，虚拟父按具体后代展开，继承展开只对同一 UUID 去重。不同 UUID 即使业务标识相同也分别返回，分页及数量按事实条目计算。需要“有几个业务实体”时，由统计显式按完整业务标识去重，并说明缺标识事实的处理。

Ossie [本体规范](https://github.com/apache/ossie/blob/main/ontology/ontology.md)用于描述概念、关系与映射；本期不输出 core-1 文档事实和证据，不能用它替代完整原生备份。
