# 与 Apache Ossie 的关系

本文说明平台为什么内部不直接使用 Ossie 文件建模、对外怎样兼容 Ossie，以及对外介绍时的准确说法。字段与转换细节以[核心模型与格式适配器设计](../design/2026-10-14-core-model-and-format-adapters.md) §1、§5–§7 为准。

## 1. 一句话

平台以 Ossie 为语义基准，内部把本体拆成可单独寻址的元素（对象、属性、关系、规则、数据集、映射、指标、文档实例），以增量方式建模；对外通过适配器导入导出 Ossie 文件，支持范围与差异公开列明。

## 2. 为什么内部按元素建模：从全量建模到增量建模

Ossie 是交换格式：一份文件完整描述一个本体，结构是树形嵌套。直接基于 Ossie 文件建模，意味着每一轮都重新生成整份文件，再与现有本体比对，即**全量建模**。平台的工作是持续编辑、审阅和问数，大多数时候只需要“对现有本体做几处修改”，因此按元素做**增量建模**：每轮只提交对具体元素的新增、修改或删除。

| 对比项 | 基于文件的全量建模 | 基于元素的增量建模（平台做法） |
|---|---|---|
| AI 每轮输出 | 整份本体文件 | 只输出要新增、修改或删除的元素 |
| 上下文开销 | 输入输出都随本体规模增长 | 输出只含改动；读取时按需检索或局部读取 |
| 定位修改对象 | 按名称比对整份文件，改名像“删旧建新” | 引用元素的固定 ID，改名不影响身份及其映射、实例 |
| 遗漏的后果 | 漏写一个对象，比对后变成删除 | 没提到的元素保持不变 |
| 并发与过期 | 无法判断基于哪一版修改 | 每条修改带基准哈希，草稿变了能发现冲突 |
| 依据 | 文件中没有逐元素证据的位置 | 每条修改带材料、行号和原文 |
| 审阅 | 只能整份接受或拒绝 | 逐条接受、拒绝、撤销 |
| 出错修复 | 整份重写，问题难定位 | 只重做被拒收的那几条 |

增量建模的优点归纳为：

1. **省上下文**：本体越大，节省越明显；AI 只关注本轮相关的元素。
2. **更精准**：每条修改指向明确的元素和版本，不会因漏写或改名误删已有内容。
3. **可追溯**：每条修改都有材料证据，审阅时能直接核对来源。
4. **可控**：人逐条决定接受与否，多人协作时冲突可被发现，不会互相覆盖。
5. **易修复**：校验失败只需修正相关条目，不必重跑整份建模。
6. **与 Ossie 解耦**：建模、审阅、发布和问数都只依赖核心模型，Ossie 只在导入导出适配器中出现。上游 Ossie 调整文件结构时（例如 2026 年 9–10 月把本体、语义模型和映射拆成独立文档），只需升级适配器，已有模型、提案和问数不受影响，也可以等上游稳定后再跟进。以后接入 Palantir Foundry、Microsoft Fabric IQ 等格式时同样只加适配器。

例：虚构的“星河零售”本体已有 40 个对象。用户补充材料后只需给“客户”增加“信用等级”属性。增量建模时，AI 只提交一条属性新增提案，并引用“客户”的 ID 和材料第 12–14 行；全量建模时，AI 需要重写全部 40 个对象，任何遗漏都会变成删除。

需要整份文件时（交给其他团队、接收他人文件），通过第 4 节的导入导出完成，与建模方式互不影响。

## 3. 复杂构造怎么处理

内部结构比 Ossie 窄，但目标是用等价结构表达同样的语义，而不是回避复杂场景：

| Ossie 构造 | 平台表达 |
|---|---|
| 多元关系 | 中间对象加二元关系 |
| 一元关系 | 布尔属性 |
| 值类型 | 属性的基础类型；独立值概念不承载 |
| 嵌套的语义模型与映射树 | 扁平的数据集登记加对象映射 |

无法等价表达的构造（例如多层嵌套映射、值概念上的关系）列在设计 §7 的支持总表和例外表中，导入时逐项写进转换报告，不静默丢弃。

## 4. 对外怎样兼容

| 方向 | 做法 |
|---|---|
| 导入他人的 Ossie 文件 | 适配器转换为提案，审阅后生效；无法确定的业务含义标为待补全，可交给 AI 以提案形式补全 |
| 导出给他人 | 从已发布版本生成 Ossie 文件，通过官方 schema 校验；损失与改写写进转换报告 |
| 完整备份与搬迁 | 使用平台原生完整包，不依赖 Ossie |

跨团队交换时，双方约定一份 Ossie 写法规范（推荐写法、会被改写的写法、不使用的写法），按规范书写的文件可以稳定往返。

## 5. 对外表述

可以说：

- 平台以 Apache Ossie 为语义基准，支持 Ossie 文件的导入与导出，支持范围和转换差异公开列明。
- 建模采用基于元素的增量方式：AI 只提交改动，每条改动可追溯依据并逐条审阅，比基于整份文件的全量建模更省上下文、更精准。

不要说：

- “完全兼容 Ossie”或“无损兼容”：部分构造会改写或不承载。
- “兼容最新 Ossie”：需注明对齐的上游提交。当前对齐 `88e0011`（2026-07-31）；上游此后已将本体、语义模型和映射拆成独立文档，并要求内嵌语义模型带 `version`；上游仍是未发布的开发版，适配器待其稳定后跟进，见[跟进待办](../plans/2026-10-20-ossie-upstream-alignment-todo.md)。
- “平台内部就是 Ossie”：Ossie 只出现在导入导出边界。
