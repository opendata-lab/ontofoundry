# 青禾生鲜超市规模测量（34 张表）

测量表多时全量建模的耗时、输出量和质量，作为“降低建模成本”设计的基线。只跑全量建模和发布 v1，不跑增量和问数。消耗模型费用（预计 1 元以内），经同意后执行。

## 输入

| 内容 | 位置 |
|---|---|
| 材料 | `material.md`（虚构的经营说明，含 11 个指标口径） |
| 业务数据 | `seed-mysql.sql`：`qinghe_mart` 34 张表、217 列，每表 3 行占位数据；其中 `ods_sync_log`、`tmp_sales_orders_bak_20250101` 是噪声表，`dim_date` 是日期维表 |

## 环境

与 `../xinghe-retail/README.md` 相同：临时 MySQL（库名 `qinghe_mart`，只读账号）、空的平台库、当前 main 的技能已装到 DataAgent。

## 步骤与固定输入

| 步骤 | 操作 | 固定输入 |
|---|---|---|
| 全量建模 | 新建工作空间，连接只读账号，同步并关联全部 34 张表，上传材料，发起建模 | 「根据材料和关联的表建立青禾生鲜超市的本体。」卡片选最接近的推荐项；计划回复「可以，按计划继续。」 |
| 发布 v1 | 全部接受并发布 | — |

## 质量参照（人工核对用，不是唯一答案）

- 业务实体约 25 个：大区、门店、员工、仓库、会员等级、会员、品类、品牌、供应商、商品、采购单及明细、入库单及明细、调拨单及明细、库存快照、盘点单及明细、销售订单及明细、支付记录、退款单及明细、促销活动、优惠券、优惠券发放、配送单、骑手、调价记录。明细可以作为实体，也可以按设计合并，需说明理由。
- 不应建模为业务实体：`ods_sync_log`、`tmp_sales_orders_bak_20250101`。`dim_date` 不建实体或只作日期维度均可。
- 关系：门店—大区、门店—店长、员工—门店、商品—品类—上级品类、商品—品牌、商品—主供应商、会员—等级、会员—注册门店、订单—门店/会员/收银员、明细—订单/商品、支付/退款/配送—订单、配送—骑手、采购单—供应商/仓库、入库—采购单、调拨—仓库/门店、盘点—门店、优惠券发放—券/会员/核销订单、促销商品。
- 指标 11 个，口径见材料“经营指标口径”；规则至少包含：只有已完成订单计入销售、退款审核通过才算完成、拒收不计库存、生鲜只能存冷链仓、临期定义、闭店门店不计在营。

## 记录

- 每步：轮数（`turn.started`）、工具调用（按类型）、工具输出字节、输入／输出 token、**墙钟时间**（发起到结束）、平台提交次数与修正轮次、提案数量（按类型）、DeepSeek 余额前后。
- 每个片段文件写入时的字节数和条数（`write` 调用的内容长度），以及有无单次输出被截断、轮数上限或折叠导致的重复读取。
- 质量：对照上面的参照，列出缺的、多的和明显错的实体、关系、指标、规则。
