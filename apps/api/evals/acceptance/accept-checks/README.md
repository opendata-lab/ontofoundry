# 接受检查验收（岚汀文具，虚构）

验证“提案可以不完整，接受时必须修好”（`docs/design/2026-11-15-accept-completeness.md` 第 10 节）：每类接受检查各埋一处问题，看是否按预期拦截或提示、消息能否直接贴进会话、智能体能否在会话里补好。同时用于第 3 步（技能变薄，本地不再检查）后的回归：提交次数、修正轮次和输出 token。消耗模型费用（预计 1 元以内），经同意后执行。

## 输入

| 内容 | 位置 |
|---|---|
| 材料 | `material.md`（经营说明＋四条近期记录，问题都埋在里面） |
| 业务数据 | `seed-mysql.sql`：`lanting_shop` 三张表。`shipments` 有物理表，首轮不同步 |

## 环境

与 `../xinghe-retail/README.md` 相同：临时 MySQL（库名 `lanting_shop`，只读账号）、空的平台库、待验证分支的技能已装到 DataAgent、Agent 提示词与 `integrations/dataagent/agents/*.md` 一致。

## 步骤与固定输入

| 步骤 | 操作 | 固定输入 |
|---|---|---|
| 1 全量建模 | 新建工作空间，连接只读账号，同步并关联 `members`、`orders`（不含 `shipments`），上传材料，发起建模 | 「根据材料和关联的表建立岚汀文具的本体，并抽取材料里的近期记录。」卡片选最接近的推荐项；计划回复「可以，按计划继续。」 |
| 2 接受 | 在审阅面板“全部接受”；被拒的逐条记下原文消息 | — |
| 3 会话补全 | 把第 2 步的拒绝消息原样贴进同一会话 | 「接受时这些没通过，请补全或说明：」＋消息原文 |
| 4 再接受 | 接受第 3 步的新提案；记录仍被拒的 | — |
| 5 同步补齐 | 在数据管理同步 `shipments` 并关联到同一会话 | 「shipments 表已同步，请补齐发货单的数据集、映射和发货件数指标。」 |
| 6 接受并发布 | 接受；被拒时按第 3 步贴消息一次；最后发布 | — |

## 预期（每项一行记入结果）

| 埋入的问题 | 材料位置 | 预期 |
|---|---|---|
| 件数写“四十二”，件数为整数 | 订单 O-2001 | AC-03 拦截；改成 42 后通过 |
| 下单时间只给日期，属性为日期时间 | 订单 O-2001 | AC-03 拦截；原文没有时间，智能体在答复中说明或补时间后通过 |
| 发货数量没写（必填） | 发货单 F-01 | AC-02 拦截；原文没有，智能体在答复中说明 |
| 会员等级“钻石”，只允许 普通／金卡 | 会员 M101 | AC-07 拦截（前提：智能体建了等级取值的值类型或规则；没建则记“未触发，缺规则”） |
| 同一订单连两个会员（多对一） | 订单 O-2002 | AC-11 拦截 |
| 下单渠道没有对应列，订单已绑定 `orders` | 订单的“渠道”属性 | AC-04 拦截（或智能体不建该属性并说明）；绑定或删除后通过 |
| `shipments` 未同步时提发货件数指标；材料列名 `ship_qty`，实际是 `qty` | 第 1、5 步 | 第 1 步不提该表的数据集（AC-10）；第 5 步列名拼错被提交检查或 AC-10 拦截，修正为 `qty` |
| 金额超过 5000 元的订单，会员须为金卡（跨对象） | 规则 | 接受订单实例时提示“规则未检查：…，涉及其他对象”，不阻止 |

## 记录

- 每项：是否触发、是否正确（误拦是最重要的结果，逐条人工核对）、拒绝消息原文、能否直接贴进会话、是否经会话补好、补全用的轮数。
- 每步：轮数（`turn.started`）、平台提交次数与修正轮次（上限 10）、提案数量（按类型）、输出 token、墙钟时间、DeepSeek 余额前后。
- 存档到 `../results/<日期>-accept-checks/`：每步 `conversation.json`、`NOTES.md`（上表逐行填结果）；存档前检查不含令牌、密码和本机路径。
