# 星河零售真实验收（可重复基线）

用同一套虚构材料、同一份业务数据和固定的提问，在干净环境里跑一遍“全量建模 → 发布 → 增量建模 → 发布 → 问数”，记录轮数、提交与修正、提案数量和问数结果，与上一次基线比较。消耗模型费用（一次约 0.4 元），低峰时段、经同意后执行。

## 输入

| 内容 | 位置 |
|---|---|
| 材料 | `integrations/dataagent/tests/fixtures/extract-retail/material.md` |
| 业务数据 | `seed-mysql.sql`：`xinghe_retail` 六张表（refunds 有物理表，但首轮不在平台同步） |
| 预期提案 | 同目录夹具：全量 `conservative/`，增量 `v1-increment.json`，增量后完整图 `supplemented/`。夹具早于“未同步表不提数据集”：全量预期为 conservative 去掉退款空列数据集（62 条），增量里退款数据集为新增而非更新 |

## 环境（每次从空开始）

1. 业务库：起一个临时 MySQL 8 容器（例如 `of-eval-mysql`，端口 3399，utf8mb4），执行 `seed-mysql.sql`，建只读账号（仅 SELECT）。复算：已完成订单 1–3 月 257.20／174.60／237.10，合计 668.90；S03 星河云桥店 317.10。
2. OntoFoundry：从当前 main 建 worktree；在平台 PostgreSQL 新建空库并执行 Alembic，API 与前端指向这个库（原库保留，结束后切回）；按全新安装初始化管理员。
3. DataAgent：从 worktree 重新打包并安装三个技能，重启后端，核对安装脚本哈希；已发布的 Agent 提示词与 `integrations/dataagent/agents/*.md` 一致，建模 Agent 轮数上限 80。
4. OpenDataWorks（问数取数）：在界面登记该 MySQL 为数据源、采集元数据，给问数用的服务账号授予只读；问数 Agent 的 OntoFoundry MCP 指向本次工作空间并发布。

## 步骤与固定输入

| 步骤 | 操作 | 固定输入 |
|---|---|---|
| 全量建模 | 新建工作空间，连接只读账号，同步并关联五张表（不含 refunds），上传材料，发起建模 | 「根据材料和关联的表建立星河零售的本体。」卡片选最接近的推荐项；计划回复「可以，商品改名为‘商品 SKU’，其余照旧。」 |
| 发布 v1 | 全部接受并发布 | — |
| 增量建模 | 在界面同步 refunds 并关联到同一会话 | 「refunds 表已同步，请补齐退款的映射、数据集和相关指标。」 |
| 发布 v2 | 全部接受并发布 | — |
| 问数 | 问数 Agent 新会话，逐题提问 | 「2026 年 1–3 月每个月的销售额分别是多少？三个月合计多少？」「云桥店 2026 年 1–3 月的销售额是多少？」 |

平台现在只允许关联已同步的表，因此 refunds 首轮只出现在材料里（2026-10-22 那次是先关联未同步表）。

## 判定与记录

- 标准答案：1 月 257.20、2 月 174.60、3 月 237.10，合计 668.90；星河云桥店（S03）317.10。
- 每步记录：轮数（DataAgent `turn.started` 事件数）、平台提交次数与结果、修正轮次、提案数量（按类型与夹具对比）、问数是否正确及读取的版本、DeepSeek 余额前后。
- 存档到 `../results/<日期>-xinghe-clean/`：每步 `conversation.json`、`run.log`、截图，以及 `NOTES.md` 的基线表；存档前检查不含令牌、密码和本机路径。
