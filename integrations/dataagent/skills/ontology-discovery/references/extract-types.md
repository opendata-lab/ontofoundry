# 类型抽取

## 决策

实体须有身份、生命周期或被引用用途；表数量不决定类型数量。属性是实例单值，关系连接两个已知类型，跨行统计交指标。先查已有归属、英文标识、同义词和范围，复用 UUID；同名多候选精确回读。

坑：订单金额100是1个属性值，不是100个金额对象；两张订单表可对应1种订单。两订单归同客户，方向订单→客户 many_to_one，反向读法仍是1条关系。购买同参与方发生2次，带数量／时间的配对按事件身份重化，不能压成1条联系。

需问：一订单签约方甲与收货人乙是否同一业务对象？推荐分别建客户与联系人，可保留2条不同关联；合并后只有1条且会丢角色差异。基数缺依据时举“1订单是否可归2客户”提问，不以 many_to_many 代表未知。

## 属性与标识

坑：地区甲／乙各有门店01，共2店；门店号单独 unique 会误认为1店，推荐地区+门店号复合标识，各分量不单独唯一。字段叫 id 或只有1行样本不能证明唯一。会员为空的订单仍可成立，不能把10单中2单无会员改成只剩8单。0和false是2个真实值，不是2项缺失。外键可有展示意义并保留为属性，关系另表达。

需问：编号01是否在两个地区重复？推荐依已有业务定义选择单标识或复合标识。七种类型按含义选择，缺少类型依据时保留已确认范围并说明，不用字符串掩盖未知；同行计算归映射。值类型：先复用已有值类型；只有材料对一类值给出统一规则时才提议新建（例如“所有金额不得为负”“会员等级只有普通、银卡、金卡”），某个字段叫金额或物理列是 DECIMAL 都不够。值类型约束只写“有值时什么值合法”，是否必填仍设在属性上；属性自己的约束只能收窄，不能与值类型矛盾（等级只允许普通/银卡/金卡时，不应再限定只允许铂金；平台不证明规则矛盾，由实例校验与人工审阅发现，见 VT-10）。抽取写法用 `show_example.py --part 01`，语义取值用 --values；本文件不加入抽取轮必读路线。

## 继承与命名

坑：父表只有E01/E02而子表有E03，父覆盖为0个E03，不能以 shared_parent 声称覆盖1个；需确认补父范围、虚拟父或独立对象。字段相似的客户和供应商各2个，不证明4个都属于同一业务类型。只存本地新增定义，继承 UUID 保留，复杂分支读 patterns。

坑：两个对象都叫“客户”而身份不同，按名称合并会由2类型变1类型；查归属和标识。稳定英文标识沿用，中文名称可重复，synonyms 表达别名；缩写X01没有依据不能展开成“信用等级1”。改名保持 UUID，按依赖修正路径与 values 键，不全局替换原文。需问同名范围时提供两个具体对象的不同身份，推荐保留独立直至明确同义。
