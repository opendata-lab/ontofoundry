# 计划与场景判断

1. 从用户消息确定范围，读完整材料索引（含历史上传）。“原文位置／表列 → 含义 → 元素 → 复用 UUID → 未决项”记入 modeling/notes.md，不回显长表。
2. 先确认“一实例／一行是什么”，区分类型、单值、联系、聚合、约束和具体实例。索引中查名称、同义词和归属；歧义定点回读。
3. 计划只确定范围与依据，不读抽取示例；协议模板可读。抽取统一转 SKILL.md 的固定包路线；修改先按 pointer 读完整旧定义。
4. 计划轮写清单与待确认后结束；抽取轮写合法范围并检查。未读范围不能当作不存在。

| 场景 | 计划产物 | 确认 | 写什么 |
| --- | --- | --- | --- |
| 全量：本体为空，首次建模 | entities.json 列全部实体 | 列表格，写待确认 | 01→05 全部片段 |
| 增量：已有本体，新增材料或表 | entities.json 列新增实体和需补充的已有实体（status 标 new／existing） | 有新增实体才确认 | 只写变化：新元素 create，已有元素按 id 精确回读后 update |
| 优化：不加新材料，改命名、重复、缺中文名或描述、映射不全、口径 | issues.json 列元素、问题、改法、影响 | 用户选编号 | 只写 update／delete，改名与合并连带依赖的规则和映射；不读材料 |
| 小改动：改名、补一个指标等 | 不写清单 | 不确认 | 直接写对应片段 |

scenario_facts 是客观事实；场景由你结合用户意图判断，写在 plan.md 首行并在回答中说明，用户可纠正。四类场景共用 modeling/ 目录、片段、检查与合并。
