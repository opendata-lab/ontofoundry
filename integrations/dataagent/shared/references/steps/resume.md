# 续做：在上一轮成果上继续

初始化打印了“上一轮未入库，基线未变，已保留其成果”。平台已确认：上一轮没有任何提案入库，本会话的草稿、材料、表和实例都没变，所以保留下来的片段仍然有效。用户为了修几处错误再发一条消息，不该让他等一次完整建模，这就是保留成果的原因。

先看用户这条消息想要什么，再对照摘要里的片段条数和最近一次检查的错误数，选一种做法。摘要已列出文件和条数，不必再 `ls` 或逐个打开片段。

| 用户这条消息 | 做法 |
|---|---|
| 只是让继续或重试（如“继续”“再试一次”） | **修正后提交**：按摘要里的错误（不够再读报告）只改报错的片段，直接按[收尾](finish.md)合并提交。不重读材料、不重读示例。 |
| 上一轮没写完（摘要里缺片段或某片段 0 条，而范围里有对应内容） | **补写缺少的部分**：按 `modeling/entities.json` 的范围只写缺的片段，查写法只看对应的 `show_example.py --part NN`，写完检查后提交。 |
| 给了新的或不同的要求（如“不要生成指标”“商品改叫 SKU”） | **改受影响的部分**：只改涉及的片段和 entities.json，必要时同步修 notes；然后检查、提交。新要求超出原范围、要新增概念时，按计划步骤先确认。注意 04 同时放指标和规则，删指标时保留规则；删掉或改名的 client_ref 要在 02–05 里一并清理引用，再用 check_part 一次检查全部片段。 |
| 要求重做、范围大改，或保留的成果读不了、和要求明显对不上 | **从头开始**：运行 `init_workflow.py --work-pack <工作包> --restart`，再按技能入口从计划开始。 |

拿不准时选改动最小、仍满足用户这条消息的做法，并在回答里说明是沿用上一轮成果做的。

- 修正轮次按本轮重新计算，仍是三轮。
- 计划模式下，凡是要改片段，先用一条简短计划说明“基于上一轮成果，改哪些片段、为什么”，获批后再改；上一轮的批准不沿用。
- 摘要已列出最近一次检查的前几条错误；不够时再读 `modeling/checks/latest-content-check.json`。摘要提示报告可能过时，就先用 check_part 重新检查。
- 所有命令都用本轮初始化打印的工作包路径；plan.md 里的工作包已改成本轮的。
